# Architecture Inventory

Last updated: 2026-08-19

This file is the current architecture handoff for humans and orchestrator agents. It is descriptive, not aspirational. Conversation Orchestrator v2 has been fully retired (see "Conversation Orchestrator v2 — Full Retirement" below) — assume legacy `/messages/process` routing owns anything not explicitly owned by Agent Runtime v3, until tests prove otherwise.

## Entry Points

- `apps/telegram-bot`: Telegram adapter. It converts Telegram updates into API calls and should stay thin. Core business logic must not depend on Telegram `ctx`, inline buttons, command menus, or hardcoded chat IDs.
- `POST /agent/message`: **the default runtime for normal Telegram chat** (`apps/api/src/agent-runtime/`), isolated from the `/messages/process` routing order below. `apps/telegram-bot` routes all normal (non-command) text here unless `TELEGRAM_AGENT_RUNTIME_V3_ENABLED=false` explicitly opts back into legacy (`routeToLegacyMessageProcessor` in `apps/telegram-bot/src/index.ts`); slash commands and Gmail OAuth/setup/sync flows are unaffected either way. Session state (topic, pending confirmation, visible entities, recent mutations, bounded message history) is persisted per `userId`+`channel` in the `AgentConversationSession` table with a sliding 24h TTL — it survives an API restart; an expired session is treated as missing. **New conversation/product work goes here, not into the legacy pipeline below.** See `apps/api/src/agent-runtime/session-store.ts`, `apps/telegram-bot/src/agent-runtime-routing.ts`, the README's "Agent Runtime v3" section, and "Legacy conversation stack to remove or isolate" below.
- `POST /messages/process`: **legacy** natural-message entry point for normal conversation. Still the production path for the explicit `TELEGRAM_AGENT_RUNTIME_V3_ENABLED=false` opt-out and for direct API callers. Purely legacy deterministic/semantic routing now — the Conversation Orchestrator v2 branch that used to run first has been retired (see "Conversation Orchestrator v2 — Full Retirement" below). Not removed yet — see the legacy inventory below for what's still needed and what isn't.
- `POST /messages/process_v2`: **retired.** This debug/audit-only endpoint (unconditional Conversation Orchestrator v2 invocation) was deleted after confirming zero production callers — see "`/messages/process_v2` Retirement" below. Conversation Orchestrator v2's own logic has since been retired too, in a later pass — see "Conversation Orchestrator v2 — Full Retirement" below.
- Domain API routes under `/users/:userId/...`: canonical mutation/read surfaces for goals, events, actions, email rules, reviews, integrations, daily loop, weekly review, planning, and debug views.
- `apps/worker`: proactive jobs for daily loop, reminders, integration sync, and Gmail background sync. It should call API/core services, not duplicate domain rules.

## Conversation Routing Order

Current production `/messages/process` order (Conversation Orchestrator v2 was the first step here until its retirement — see "Conversation Orchestrator v2 — Full Retirement" below; the order below is what's left, unchanged otherwise):

1. Parse request body and ensure user.
2. Expire stale pending decisions.
3. Handle standalone `now` safely.
4. Run deterministic policy/guardrail precheck.
5. Resolve pending decisions before ordinary routing when the reply fits the pending scope.
6. Handle focused pending Gmail rule creation/editing.
7. Reject unresolved hygiene follow-ups without a visible context.
8. Route planning requests.
9. Route explicit memory requests.
10. Re-run guardrail check before surface routing.
11. Route deterministic conversation surfaces.
12. Route optional legacy LLM semantic router.
13. Try manual action creation.
14. Block unhandled mutation/control verbs from generic chat.
15. Route custom goal progress and structural proposals.
16. Optionally analyze with OpenAI and create extracted events.
17. Compose final response.

## Route Ownership Map

Conversation Orchestrator v2 has been retired (see "Conversation Orchestrator v2 — Full Retirement" below) — there is no more split ownership between v2 and legacy. Everything below is owned by legacy `/messages/process` routing:

- All slash command behavior and command batching.
- All Gmail rule creation/editing/removal conversations (only `gmail.rule.create`/`.list`/`.explain` and `gmail.review.*` have a v3 equivalent — see "Legacy Conversation Stack To Remove Or Isolate" below for what v3 does and doesn't cover).
- Planning sessions, weekly planning edits, and plan creation replies.
- Daily loop settings mutations.
- Action hygiene list creation and bulk/multi-item hygiene replies (v3's `action.*` tools are single-item only).
- Recent mutation status questions.
- Explicit memory creation, conservative progress logging, and selected read surfaces — v3 independently reimplements these for its own default Telegram path, but the legacy versions inside `/messages/process` are unchanged and still what direct API callers and the legacy opt-out hit.
- Generic chat/coaching fallback.
- Legacy LLM semantic routing for natural-language surfaces v3's tool catalog doesn't cover.
- Event extraction and final response composition after legacy OpenAI analysis.

Route debug contract (fields still populated by the remaining legacy routers):

- `plannerUsed`
- `llmPlannerAttempted`
- `llmPlannerUsed`
- `legacySemanticAttempted`
- `legacySemanticUsed`
- `handledBy`
- `mutationExecuted`
- `policyPrecheckResult`

`v2Enabled`, `llmOperationPlannerEnabled`, `v2SkippedReason`, and `operationPlanValidated` were Conversation Orchestrator v2 debug fields. They remain defined (as optional fields) in the shared `ProcessMessageResult.routeDebug` zod schema in `packages/core/src/message-processing.ts` for backward compatibility with any external consumer of the API response shape, but no code populates them anymore — treat them as dead schema, not live contract.

`policyPrecheckResult` is safe and compact. Expected values include `passed`, `reference_text_blocked`, and `blocked_by_guardrail`.

## Risk And Guardrail Generalization Plan

Current implementation is betting/trading-heavy because that was the first real hard-stop domain. Keep the behavior, but generalize the architecture language:

- Rename product-facing concepts toward `policy guardrail`, `risk-control goal`, and `blocked action` where possible.
- Keep betting/trading as one policy domain, not the entire risk engine.
- Future domains can include health, spending, sleep, social media, or custom user-defined no-go rules.
- Do not create actions, plans, or Gmail rules that help bypass a hard guardrail.
- Do not let LLM advice optimize restricted behavior. It may support safe refusal or cooldown language only.

## PendingAction / Agent Runtime v3 Interop

**The bug:** making Agent Runtime v3 the Telegram default meant a legacy `PendingAction` row (created by a slash-command flow like `/action_hygiene`, or a Gmail rule proposal) could be silently ignored, misrouted, or reinterpreted as a fresh request the moment the user replied in plain natural language instead of running `/confirm`/`/cancel` — because v3's context loader never read the `PendingAction` table at all.

**Chosen fix: Option A** — v3 detects the legacy `PendingAction` itself, in-process, every turn. Option B (a Telegram-layer routing bridge back to the legacy resolver) was available but not needed: the only genuinely unsafe part of the legacy resolver is `applyPendingAction`'s type-specific mutation logic (Gmail rule archival/creation, action-hygiene batch operations, profile updates, etc.), and that function was never going to be called from v3 either way — bridging the whole message back to `/messages/process` would have re-introduced exactly the "v3 and legacy both handle the same message" risk the hard rules forbid, for no benefit. Detecting the row and using only the two safe, already-package-level DB functions (`getLatestPendingAction`, `rejectPendingAction` — both plain `@operator-agent/db` calls, zero server.ts dependency, zero circular-import risk) is strictly safer and simpler.

**Behavior, by message type, when a legacy `PendingAction` is active:**
- **v3's own `session.pendingOperation` is checked first, unconditionally.** If v3 itself has an open confirmation (e.g. a pending Gmail rule creation), an exact "yes"/"no" resolves *that* — the legacy row is left completely untouched. The two pending-state systems are never both consulted for the same message; v3's own state always wins when present. This is what keeps them from ever being confused with each other.
- **Exact confirm** (v3's existing whitelist: "yes", "confirm", "ok", "sí", etc.), only when v3 has no pending operation of its own: v3 does **not** execute the legacy `PendingAction`. `applyPendingAction`'s mutation logic is entangled with Gmail-rule and action-hygiene helpers that aren't safely importable into `agent-runtime/` without a circular import back into `server.ts` — and calling the DB-level `confirmPendingAction` without running that logic would mark the row "confirmed" while silently skipping the actual mutation, which is worse than doing nothing. Reply: *"I can't safely apply that kind of pending action from here yet. Reply with /confirm to complete it, or /cancel to drop it."* The row is left untouched, still `status: "pending"`.
- **Exact cancel** (v3's existing whitelist: "no", "cancel", "stop", etc.): v3 calls `rejectPendingAction` directly and marks the row rejected. This is safe to execute automatically because rejecting never runs any of `applyPendingAction`'s type-specific logic — it only flips a status column, identical in effect to what `/cancel` already does. Reply: *"Cancelled. I did not change anything."* (matching the existing legacy `/cancel` reply text exactly).
- **Anything else** (an ambiguous or unrelated normal message): the planner is never invoked. Reply: *"You have a pending action from the previous flow: `<summary>`. Confirm, cancel, or continue with a new request."* This mirrors the exact same "block until resolved" pattern v3 already uses for its own `pendingOperation` firewall (`"You still have a pending confirmation for X. Confirm, cancel, or tell me a new request."`), so it isn't a new UX pattern — it's the existing one, applied consistently to the legacy case too.
- **No `PendingAction` at all:** zero behavior change — the check is a no-op and the turn proceeds exactly as before.

**Where it lives:** `ContextBundle.legacyPendingAction` (`apps/api/src/agent-runtime/types.ts`), populated by `context-loader.ts` via `getLatestPendingAction(userId)` alongside the rest of the per-turn context fetch. The branching logic is in `runtime.ts`'s `processAgentMessage`, right after the existing exact-confirm/cancel checks for v3's own `pendingOperation` and before the planner is ever invoked. `AgentDebugInfo.legacyPendingActionDetected` exposes whether this path was taken, for tests and observability. Deliberately kept as a separate `ContextBundle` field rather than merged into `AgentSessionState`/`session.pendingOperation` — they are unrelated mechanisms (one is v3's own in-session state, the other is fresh-fetched legacy DB state) and conflating them was the whole failure mode being fixed.

**What remains legacy (not migrated by this change):**
- `applyPendingAction` itself, and everything it calls (Gmail rule archive/create, action-hygiene batch operations, profile/goal/memory mutations) — still `server.ts`-only, still only reachable through `/confirm` or the legacy `/messages/process` confirmation branch. This change does not migrate action hygiene, Gmail rule handling, or any `PendingAction` type's actual execution to v3 — it only stops v3 from *ignoring* the row's existence.
- The action-hygiene natural-language batch parser (row 6 in the audit table above) — still needed for anyone replying with hygiene-specific syntax ("archive 1, 2", "all except the read one") via `/confirm`-adjacent legacy paths; v3 does not understand that syntax and isn't expected to yet.
- `/pending`, `/confirm`, `/cancel` slash commands — completely unchanged; they still hit the same HTTP routes as before, unaffected by anything v3 does.

**Safe deletion/further-migration conditions:** v3 could take over *executing* legacy `PendingAction`s (not just detecting them) once `applyPendingAction`'s Gmail-rule and action-hygiene dependencies are themselves extracted into safely-importable modules — i.e. after the "migrate-first" work already queued for rows 3/6/7 in the audit table above. Until then, this detect-defer-or-safely-cancel design is the stopping point, and should not be treated as "done, no further work needed" — it closes the silent-ignore bug, not the broader migration.

## Strategy Change — Capability Migration Into Agent Runtime v3

Starting with this pass, `server.ts` line-count reduction is no longer the primary goal of this cleanup series. Agent Runtime v3 is now the default Telegram normal-chat runtime and `/messages/process` (legacy) has already been fully extracted (see "`/messages/process` Third Extraction Readiness Audit" above). The new goal is to migrate complete user-facing capabilities from the legacy `/messages/process` brain into Agent Runtime v3's typed tool catalog one at a time, verify Telegram actually uses v3 for each migrated capability, and only delete the corresponding legacy code once it is provably unreachable and every route/slash-command path is still safe. Each migration pass gets its own dated section below, following the "Migration Rule" steps above. Legacy code is not deleted as part of a migration pass unless explicitly confirmed unreachable — see each pass's "What remains legacy" note.

## Action Hygiene Migrated Into Agent Runtime v3

**Goal:** make Agent Runtime v3 handle the action-hygiene cleanup flow ("clean up my actions") entirely in normal Telegram conversation, without falling back to legacy `/messages/process`, following the Migration Rule above.

**V3 capability map before this pass:** the tool catalog had `action.list`/`action.create`/`action.snooze`/`action.complete`/`action.archive` — all single-action tools operating on one `actionId` at a time, with the validator auto-resolving an omitted `actionId` only when *exactly one* action entity was visible in `session.visibleEntities`. There was no way to show a *numbered, multi-item* cleanup list and no way to reference an item by its position in one ("complete 1"). `operator.today`'s summary already promised `'Tell me "clean up my actions" and I'll help you decide what to complete, snooze, or archive.'`, but nothing in the v3 tool catalog could fulfill that promise — the phrase would have fallen through to the planner with no matching tool.

**Reusable logic found in `apps/api/src/legacy/action-hygiene-conversation.ts`:** `analyzeActionHygiene` (candidate detection: stale/overdue/low-priority-untouched action items) and its formatting siblings `actionHygieneVisibleActions`/`cleanupDecisionGrammar` were pure, DB-read-only functions with zero dependency on the legacy `PendingAction` row — already reused by four other modules (`legacy/weekly-review-conversation.ts`, `legacy/daily-conversation.ts`, `operator/attention.ts`, `server.ts`'s own `/actions/hygiene` debug route) before this pass, all importing from the legacy file. Per the task's explicit instruction, these moved into a new non-legacy module, `apps/api/src/actions/hygiene-session.ts`, and all five consumers (including the legacy file itself) now import from there instead. `apps/api/src/actions/hygiene.ts`'s `applyActionHygieneBatchOperations` — the actual DB-mutation batch executor (complete/snooze/archive/keep, including goal-progress-on-completion) — was already non-legacy and reused as-is by the new v3 tools, with zero duplication.

**V3 operations added** (`apps/api/src/agent-runtime/tool-catalog.ts`):
- `action.hygiene_start` (`mutates: false`, no confirmation): shows the user's action-cleanup candidates. Empty args — always operates on the current user's own open actions via `analyzeActionHygiene`.
- `action.hygiene_apply` (`mutates: true`, no confirmation — matching the existing precedent that `action.snooze`/`action.complete`/`action.archive` don't require confirmation either, since these are easily-undone, low-blast-radius mutations): applies complete/snooze/archive/keep decisions to one or more actions from the most recently shown hygiene list in a single operation. Args are a structured `selections` array (`{ index?, actionId?, decision, snoozeUntilText? }`, 1–10 items, one entry per decision the user made), not a raw text blob — "complete 1, snooze 2 to Friday, archive 3" becomes three selection objects in one operation, not three separate tool calls or a parsed string.

**Planner/schema infrastructure extended, not duplicated:** `action.hygiene_apply`'s `selections` is the first tool arg in this codebase to need an array-of-objects shape. Rather than flattening it into multiple single-decision tool calls (which would have lost the ability to compose one combined "Done: ..." reply — see below), `tool-catalog.ts`'s planner-JSON-schema generator (`toolArgsPlannerJsonSchema`/`zodFieldToPlannerJsonSchema`) was made recursive to support nested `ZodArray`/`ZodObject` fields generically, for any future tool that needs one. `validator.ts`'s `stripNulls` (which normalizes OpenAI Structured Outputs' "omitted optional field → explicit JSON `null`" convention before zod validation) was likewise made recursive, since it previously only processed the top-level args object and would have rejected a `null` inside a nested selection.

**Session/visible-entity behavior:** `AgentEntity` (`apps/api/src/agent-runtime/types.ts`) gained an optional `index?: number` field — the 1-based position in the most recently shown numbered list. `action.hygiene_start`'s executor tags each surfaced action entity with its list position; these become `session.visibleEntities` via the existing "operation result entities replace the session's visible set" mechanism (unchanged). `action.hygiene_apply`'s validator resolves each selection's `actionId` deterministically against `context.session.visibleEntities` by matching `type === "action" && index === selection.index` — never against hidden LLM memory of the conversation. A selection that already carries a direct `actionId` (e.g. the planner matched a title like "the gym one" to a visible entity itself) is trusted as-is, matching the existing precedent for `action.snooze`/`complete`/`archive`. If **every** selection in an `action.hygiene_apply` operation fails to resolve — most commonly because no hygiene list is currently visible — the whole operation returns `needs_clarification` and nothing executes; if only some fail, the rest still apply and the unresolved ones are reported as skipped in the reply, the same way `applyActionHygieneBatchOperations` already reports "no longer found" for a deleted action. An exact `"cancel"` (already-deterministic, whitelisted, checked before the planner runs) now also clears `session.visibleEntities` in both of its no-op branches, so a stray later "complete 1" can't resolve against a stale list — `action.hygiene_apply` never sets a `pendingOperation`, so there was nothing else for cancel to clear for this flow specifically, but this reset is harmless and correct for every topic.

**Response composition:** `action.hygiene_start`'s multi-line "Here are the actions worth cleaning up: ... Reply like: complete 1, snooze 2 to Friday, archive 3." summary is returned verbatim by the existing `mutates: false` informational-tool path in `response-composer.ts` (unchanged). `action.hygiene_apply` was added to `GROUND_TRUTH_ONLY_TOOLS` alongside `operator.recent_changes`/`gmail.rule.create` so its single combined `applyActionHygieneBatchOperations` reply ("Done: - Archived X - Completed Y ...") is returned verbatim rather than being sentence-joined/mangled by the generic mutation-summary path.

**Files created:** `apps/api/src/actions/hygiene-session.ts` (pure candidate-analysis, shared by legacy and v3). **Files changed:** `apps/api/src/legacy/action-hygiene-conversation.ts` (re-points to the new shared module, net smaller), `apps/api/src/legacy/weekly-review-conversation.ts`, `apps/api/src/legacy/daily-conversation.ts`, `apps/api/src/operator/attention.ts`, `apps/api/src/server.ts` (import source updated only, zero behavior change), `apps/api/src/agent-runtime/{types,tool-catalog,validator,executor,response-composer,planner,runtime}.ts`.

**What remains legacy, and why:** `apps/api/src/legacy/action-hygiene-conversation.ts`'s free-text batch/single-item reply parser (`resolveActionHygieneReply` and its `planActionHygieneBatchReply`/`tryPlan*` cluster) and `createActionHygieneSession`/`storeActionHygieneSession` (which write a legacy `PendingAction` row) are unchanged and still live — they back the `GET /users/:userId/actions/hygiene` and `POST /users/:userId/actions/hygiene/reply` HTTP routes (the implementation behind Telegram's `/action_hygiene` and `/debug_action_hygiene` slash commands) and the legacy `/messages/process` conversational path, both explicitly out of scope for deletion per this task ("do not delete legacy action hygiene yet unless it becomes provably unreachable and all routes/slash commands are still safe" — slash commands still call it directly, so it is reachable and stays).

**Tests:** `tests/agent-runtime-action-hygiene.test.ts` (new, 11 tests) — hygiene_start returns candidates and a clean-list message, visible entities are stored with correct indices, complete/snooze/archive/keep each mutate the correct action via index resolution, a multi-decision reply ("complete 1, snooze 2 to Friday, archive 3") applies all three in one operation, "complete 1" with no visible hygiene session asks for clarification and mutates nothing, "cancel" clears visible session state and a subsequent stray "complete 1" no longer resolves, and "yes" with nothing pending gives the fixed no-pending reply (hygiene_apply never creates a pendingOperation). All existing tests — `tests/actions-hygiene.test.ts` (legacy batch-operation unit tests), `tests/agent-message.test.ts` and other `agent-runtime-*.test.ts` files (v3 memory/Gmail/today/session-persistence), `tests/messages-process-legacy.test.ts` — pass unchanged; full suite is 235/235 (224 before this pass + 11 new).

**Validation:** `pnpm typecheck` (all 6 packages), `pnpm build` (all 6 packages), `pnpm test` (235/235 passing), `git diff --check` — all clean.

## Next-Week Planning Migrated Into Agent Runtime v3

**Goal:** make Agent Runtime v3 handle "plan next week" (propose → adjust → confirm) entirely in normal Telegram conversation, without falling back to legacy `/messages/process`, following the Migration Rule above.

**V3 operations added** (`apps/api/src/agent-runtime/tool-catalog.ts`):
- `planning.next_week_start` (`mutates: false`, no confirmation): builds the plan context, generates suggestions via the shared `generateNextWeekPlanSuggestions`, filters to creatable new suggestions only (`isCreatableNewPlanSuggestion` — reused as-is; cleanup/already-covered suggestions are intentionally not shown in v3's simpler flat list, unlike legacy's three-section debug-style format), and shows a numbered draft.
- `planning.next_week_edit` (`mutates: false`, no confirmation — deliberately non-mutating so the pending-operation firewall never blocks it while a draft is open): applies `removeIndexes`/`changes: [{index, dueText}]` to the currently open draft and re-shows it. (Extended by a later hotfix pass to also accept natural-language references — see "Next-Week Planning Hotfix — Deterministic Edits and Natural-Language UX" below.)
- `planning.next_week_apply` (`mutates: true`, no confirmation, but never planned by the LLM directly — see below): creates the action items for the current draft's selections, reusing `actionInputFromPlanSuggestion` + `findEquivalentOpenPlanAction` (dedup against existing open actions) + the already-non-legacy `createActionItemIfNotExists`, exactly the same DB-mutation path `resolveNextWeekPlanReply`'s "create" branch already used — zero duplication.

**New generic runtime mechanism — `ExecutedOperation.pendingOperationUpdate`:** action-hygiene's confirmation model doesn't fit planning's propose→adjust→confirm loop. The existing `needs_confirmation`/`requiresConfirmation: true` mechanism (used by `gmail.rule.create`) never actually *executes* the tool on the proposing turn — it only stores the LLM's own args and later describes them statically. But a plan draft must actually run (real DB reads, real suggestion generation) to show real data, and its edits ("remove 2") must not be blocked by the pending-operation firewall, which blocks any newly-planned *mutating* tool while something is pending. The fix: `planning.next_week_start`/`next_week_edit` are modeled as ordinary `mutates: false` "valid"-status operations (so they execute normally and pass the firewall), and their executors set a new `ExecutedOperation.pendingOperationUpdate` field (`{ topic, summary, operations } | null`) to directly install/replace/clear `session.pendingOperation` as a side effect — `runtime.ts`'s `applyExecutionSideEffects` applies it after every turn's executed ops, independent of and in addition to the existing `pendingConfirmationOps`-driven auto-population (which only ever fires for `needs_confirmation`-status ops, so the two paths never collide for the same tool). Absent/undefined is a complete no-op for every other existing tool. `planning.next_week_apply` itself is rejected as `invalid` by the validator if the LLM ever plans it directly (`revalidateForExecution`, the only path used when the user's exact "yes" re-executes a stored `pendingOperation`, does not call the validator at all, so this only blocks a fresh/fabricated plan, never the real confirm path) — this is the only way `session.pendingOperation` can ever be installed with a *mutating* tool inside it while still being safe, since nothing except the exact confirm whitelist can ever cause it to run.

**Whitelist addition:** `"looks good"` was added to `runtime.ts`'s `CONFIRM_WHITELIST` (task-specified example phrase); `CANCEL_WHITELIST` was unchanged (`"cancel"` already covered the planning example).

**Session/visible-entity behavior:** `AgentEntity.type` gained a `"plan_suggestion"` member. Both `next_week_start` and `next_week_edit` tag each shown draft item with its 1-based position, which becomes `session.visibleEntities` via the existing entities-replace-visible-set mechanism (unchanged). The validator gates `planning.next_week_edit` on an open draft existing (`session.pendingOperation.operations[0].tool === "planning.next_week_apply"`) and on `removeIndexes`/`changes` not both being empty, in both cases returning `needs_clarification` with nothing executed — no LLM-memory-based resolution.

## Next-Week Planning Hotfix — Deterministic Edits and Natural-Language UX

**Trigger:** a real Telegram transcript surfaced a bug in the pass above. "remove 1" replied `"the plan was missing required details (needs: removeIndexes.0). Nothing was changed."`, yet the *next* turn's re-shown draft had item 1 already gone — a session mutation despite a reported validation failure, violating the runtime's core "invalid → nothing executes" guarantee. The same pass also carried a UX request: numbered commands ("remove 2", "change 1 to Tuesday") are too mechanical; natural references ("remove the YouTube one", "move the gym one to Friday") should work too, with numbers kept only as a fallback.

**Root cause, part 1 — planner JSON schema generator bugs (`apps/api/src/agent-runtime/tool-catalog.ts`):** `zodFieldToPlannerJsonSchema` had two pre-existing bugs that this pass exposed for the first time, because `planning.next_week_edit`'s `removeIndexes`/`changes` were the first *optional top-level array* fields in the tool catalog (`action.hygiene_apply`'s `selections` array is required, not optional, so it never hit this path).
1. **No `.describe()` propagation.** The generator built `{type, items, enum, ...}` nodes but never read zod's `.description`, so none of the schema's helpful guidance — including `removeIndexes`' "1-based positions" wording — ever reached the real OpenAI request. With no explicit contract on indexing base, the live model plausibly emitted a 0-based `removeIndexes: [0]` for "remove 1", which fails `z.number().int().positive()` — exactly the reported `needs: removeIndexes.0` error.
2. **Missing nullable-array handling.** Every sibling branch (`ZodEnum`/`ZodNumber`/`ZodBoolean`) checked `optional` and added `"null"` to the JSON type, so OpenAI's strict mode (which requires every property in `required`, modeling optionality via nullability instead of omission) had a schema-valid way to represent "not set." The array branch never did this — an optional array field like `changes` had no null-safe way to be left out.

Both are now fixed generically in `zodFieldToPlannerJsonSchema` (rewritten to build every branch's schema first, then layer on `description` if `field.description ?? inner.description` is set, and the array branch now emits `{type: ["array", "null"], items}` when optional) — this improves every tool's schema, not just planning's, since the descriptions were always being silently dropped.

**Root cause, part 2 — non-atomic edit execution:** the original `planning.next_week_edit` executor resolved `removeIndexes` and `changes[].index` against the current draft *per-item*, independently, inside the executor itself. A call combining a stale `removeIndexes` (e.g. carried over by the LLM from an earlier, failed turn — the planner had no explicit instruction not to repeat an unfulfilled prior request) with a `changes` entry for that same index would silently apply the removal and drop the change with no error, appearing to "partially succeed" even though the whole operation was never validated as a coherent whole.

**Fix — atomic, validator-side resolution:** all resolution for `planning.next_week_edit` — numeric index existence, natural-ref matching, day-text parsing — now happens once, up front, in `validator.ts`'s `resolveNextWeekEditArgs`, before anything executes. It is all-or-nothing: if any index/ref/day fails to resolve against the *current* draft, the whole operation returns `needs_clarification` and the executor never runs — `session.pendingOperation`/`visibleEntities` are provably untouched (`revalidateForExecution`/the executor are never reached for an invalid or unresolved edit). Only after full resolution does the validator rewrite `args` to a plain, pre-resolved shape (`{removeIndexes: number[], changes: [{index, dueAt}]}`) that the executor applies without re-resolving anything itself — the executor now *trusts* the validator completely for this tool, which let its own `planning.next_week_edit` case shrink substantially (no more per-item "notes"/partial-match bookkeeping). This closes the exact failure mode from the transcript: an invalid "remove 1" can no longer leave any trace in the stored draft, and a follow-up "change 1 to Tuesday" is guaranteed to still see the *original*, unmutated item 1.

**Natural-language references, added to `planning.next_week_edit`'s schema:**
- `removeRefs: string[]` — natural-language item descriptions to remove (e.g. `"the YouTube one"`, `"reading"`), alongside the existing `removeIndexes`.
- `changes[].ref` — a natural-language alternative to `changes[].index` (exactly one of `index`/`ref` per entry; `index` wins if the planner ever sets both).
- `keepIndexes` / `keepRefs` — inverse selection for "keep X and remove the rest" style requests: every item *not* matched is removed.
- `lighter: boolean` — "make it lighter"/"make it shorter" requests. Deliberately a bare flag, not LLM-chosen indexes: the LLM signals *intent*, and code alone decides *what* to drop.

Numeric `removeIndexes`/`changes[].index` remain fully supported as an explicit fallback (`"remove 2"`, `"change 1 to Tuesday"` still work exactly as before) — they are no longer the *primary* UX the response copy pushes the user toward (see below), but nothing about them changed mechanically.

**Deterministic resolution (`apps/api/src/planning/next-week.ts`, new exports):**
- `resolvePlanSuggestionRef(ref, current)` — matches a natural-language ref against the current draft's own `title`/`goalTitle` text only, never hidden LLM memory or an invented id. Resolution order: exact normalized-title match first; then a fuzzy token match (`planTokensMatch`, a common-prefix comparison — not a real stemmer, but enough to bridge "job"/"jobs", "read"/"reading", "apply"/"applications" without over-matching unrelated words like "car"/"care"). Zero matches → `{status: "none"}`; more than one → `{status: "ambiguous"}` — the validator turns either into a clarification question and executes nothing, per the same "do not mutate anything on ambiguous/no match" rule the numeric path already followed.
- `computeLighterPlanRemoval(current)` — the deterministic "lighter" logic. Only acts when there is a clear, strictly-smaller subset of lower-priority items (`actionPriority === "low"` first, falling back to the suggestion's own goal `priority`); if every item is the same priority, or the draft has 2 or fewer items, it returns `{status: "unclear"}` rather than guessing — this is what keeps "make it lighter" from ever hallucinating or dropping a high-priority item.

Because "the gym one" doesn't share a literal word with the generated suggestion title ("Do 2 strength sessions"), resolving it depends on the *underlying goal's own title* containing "gym" (carried through as `suggestion.goalTitle`, which is part of the search text) — a real but data-dependent bridge, not a hardcoded synonym table. The planner prompt (below) is the other half of this: the LLM is expected to try mapping a natural description to a visible item's `index` itself first (it already sees full draft titles in context), falling back to `removeRefs`/`changes[].ref` only when it genuinely can't.

**Planner prompt (`planner.ts`) updated:** indexes are now explicitly described as "always 1-based... the first item is 1, NEVER 0"; guidance on when to use an index vs. a ref vs. `lighter`; and an explicit instruction not to repeat an earlier turn's edit request just because it appeared not to take effect — the user will say it again if they still want it. This directly targets the prompt-level contributor to the root cause above.

**Response copy fixed:**
- `"Here's a draft plan for next week plan:"` (a title/window-phrase duplication bug — `formatPlanDraftSummary` was interpolating `formatPlanTitle()`'s report-style title, "Next week plan", into a sentence already ending in "plan for ...") → `"Here's a draft plan for next week:"`. The function now takes `windowKind` directly and phrases it inline ("next week"/"this week") instead of reusing the report-title helper.
- `"Reply: yes, remove <n>, change <n> to <day>, or cancel."` → `"Tell me naturally what to change — for example: \"move the gym one to Friday\", \"remove the YouTube item\", \"make it lighter\", or \"yes\" to create it."` — natural phrasing first; numbered commands still work but are no longer what the bot itself suggests.

**Files changed:** `apps/api/src/agent-runtime/tool-catalog.ts` (schema-generator fixes, extended `planning.next_week_edit` schema), `validator.ts` (`resolveNextWeekEditArgs`, atomic resolution, date parsing moved here), `executor.ts` (simplified `planning.next_week_edit`/`next_week_start` cases, copy fixes), `planner.ts` (prompt guidance), `apps/api/src/planning/next-week.ts` (`resolvePlanSuggestionRef`, `computeLighterPlanRemoval`), `tests/agent-runtime-next-week-planning.test.ts`.

**Tests:** 13 new — schema-invalid and unresolvable-index edits both leave `pendingOperation`/`visibleEntities` byte-for-byte unchanged and create nothing in the DB; "remove 1" now succeeds outright with no validation error; a prior invalid edit is proven not to bleed into a subsequent "change 1 to Tuesday" (still the original item 1); the reply never contains the "next week plan:" duplication; `"remove the YouTube one"`, `"move the gym one to Friday"`, `"remove reading"`, and `"keep job applications and remove the rest"` all resolve deterministically against a 5-goal seeded draft; an ambiguous ref (two fallback-draft items both mention "review") and an unknown ref both ask for clarification and mutate nothing; `"make it lighter"` is tested on both branches — a clean low-priority-item removal, and an "unclear" clarification when three real suggestions share the same priority. Full suite: **258/258** (245 before this pass + 13 new).

**Validation:** `pnpm typecheck` (all packages), `pnpm build` (all packages), `pnpm test` (258/258 passing), `git diff --check` — all clean.

## Next-Week Planning V3 State-Machine Hardening (committed: `fix: harden v3 planning state machine`)

**Trigger:** real Telegram smoke testing (not unit tests, which all passed) found the planning hotfix above still had multi-turn state bugs: a generic "Agent v3 hit an error" on some first-ever "plan next week" turns; "move the jobs to Friday" on a single-item draft either emptied the plan or, in a follow-up fix pass, got rejected outright with "That would remove everything" even for a plain move (the live planner does not reliably follow the "never also list it in removeIndexes/removeRefs" prompt instruction, and repeatedly sends a redundant remove alongside the change for the exact item it's moving); "show me the week plan" regenerated a brand-new draft instead of showing the current one; and a rejected edit's reply could still contain the planner's own pre-execution `replyDraft` falsely claiming success ("I've moved the job application to Friday" glued onto a rejection).

**Root causes and fixes, each with a regression test:**
- **First-turn error:** `context-loader.ts`'s `loadContext` ran `ensureUser(userId)` (creates the `User` row) inside the same `Promise.all` as other user-scoped queries that have a foreign key to `User.id` (e.g. `getOrCreateUserOperatingProfile`) — on a brand-new user's first-ever message these can race, and the FK insert can land before `ensureUser`'s own insert commits. Fixed by awaiting `ensureUser` first, sequentially. As defense-in-depth (the exact race is timing-dependent, not reliably reproducible in a fast local test run), `runtime.ts`'s `processAgentMessage` also gained a top-level try/catch: any unexpected exception anywhere in a turn now produces a graceful, honest reply instead of crashing the request and surfacing the Telegram layer's generic dev-safe error text.
- **Non-atomic edit execution:** the original executor resolved `removeIndexes`/`changes[].index` independently, per-item. A request carrying both a remove and a change for the same item would filter it out first, leaving nothing for the change to apply to. Fixed with fully atomic resolution in `validator.ts`'s `resolveNextWeekEditArgs`: every index/ref/day resolves against the current draft *before* anything executes, and — critically, refined across two fix passes — **an explicit change to an item always wins over a redundant remove of that same item**, whatever combination produced the conflict (a raw arg, keep-inversion, or "lighter"); only once that cancellation is applied does the function check whether the edit would still remove every remaining item, which is rejected unless the user explicitly set `removeAll: true`. The first version of this guard (reject-if-empty with no change-wins cancellation) was itself a live-testing-only bug: it made a plain "move the jobs to Friday" permanently unusable on a single-item draft, because the redundant remove the real planner kept sending made every attempt look like "remove everything."
- **Regenerated instead of current draft:** there was no tool for "show me the current draft" — the planner had only `planning.next_week_start`, which always rebuilds from scratch. Added `planning.next_week_show_current` (`mutates: false`, read-only, never touches `pendingOperation`/`visibleEntities`), with prompt guidance to use it for view requests and never `next_week_start` while a draft is open.
- **False success claims:** `response-composer.ts`'s `composeReply` blended the planner's own pre-execution `replyDraft` into *every* clarification reply, including ones where the attempted operation was rejected by the validator. Fixed: a clarification reply is now composed from the clarification question alone, never blended with `replyDraft` — this was a real, generically-applicable bug (not planning-specific), just first surfaced by planning's multi-turn edit flow.

**Dev/test-only planning trace:** `AGENT_RUNTIME_PLANNING_TRACE=true` (unset/off in every real deployment) populates a new `debug.planningTrace` field on any turn touching a planning tool or a planning pending operation — message, planned tool/args, validation status/error, resolved args, executor status/summary, `pendingOperation`/`visibleEntities` before and after, and which `composeReply` branch produced the reply — and logs it via `console.log`. Built in `runtime.ts` (`recordPlanningTrace`/`inferComposerSource`), exposed via `response-composer.ts`'s new `isGroundTruthOnlyTool` export so the trace's composer-source inference doesn't duplicate `composeReply`'s own branch logic.

**Files changed:** `apps/api/src/agent-runtime/{context-loader,runtime,response-composer,tool-catalog,validator,executor,planner,types}.ts`, `tests/agent-runtime-next-week-planning.test.ts`.

**Tests:** 12 new across the two fix passes (first-turn safety net, the full remove→remove→move chain reproducing the exact transcript, "show current" not regenerating, the empty-plan guard, the redundant-remove-vs-change conflict in both ref and numeric-index form, the false-success-claim fix, pendingOperation/visibleEntities sync invariants, and the dev-trace itself). Full suite: **270/270** (258 before this pass + 12 new).

**Validation:** `pnpm typecheck`, `pnpm build`, `pnpm test` (270/270), `git diff --check` — all clean.

**Lesson carried into the next pass:** every one of these bugs was a *multi-turn state* bug — individually-correct single-tool unit tests passed throughout, but the state carried between turns (a stale index, a regenerated draft, a leaked pre-execution claim) was still wrong. This is what motivated the scripted conversation smoke/eval harness below.

## V3 Scripted Conversation Smoke/Eval Harness

**Goal:** a lightweight way to replay the exact multi-turn conversation shapes that found the bugs above automatically, instead of requiring a human to retest them by hand in Telegram after every change — explicitly *not* a general eval framework, and explicitly not a replacement for real Telegram smoke testing (still the only way to see what the real planner actually sends, as the hardening pass above shows).

**Design:** two small helper modules plus one test file, all under `tests/`, deliberately outside `apps/api/src` so the harness can never be imported by production code and is never part of any package's own `tsc` build:
- `tests/helpers/agent-runtime-test-helpers.ts` — the generic primitives (`MockPlan`, `op`, `mockPlan`, `clearAgentRuntimeMocks`, `seedUser`, `sendAgentMessage`, `getAgentSession`) extracted from the near-identical copies that had accumulated across `tests/agent-message.test.ts`, `tests/agent-runtime-action-hygiene.test.ts`, and `tests/agent-runtime-next-week-planning.test.ts`. Existing test files were left untouched (this is additive, not a refactor of already-passing tests) — new scripted scenarios build on the shared module instead of copying the boilerplate a fourth time.
- `tests/helpers/agent-runtime-scripted-eval.ts` — `runScriptedScenario(server, userId, scenario)`: runs a fixed sequence of `{message, plan?, assert?}` turns through `POST /agent/message` (the exact route `apps/telegram-bot/src/agent-runtime-routing.ts` calls for real Telegram traffic), reading the session row directly before/after each turn for `pendingOperation`/`visibleEntities`, and returning a full `CapturedTurn[]` transcript. Also exports small reusable assertion helpers matching the invariants scripted scenarios most often need: `assertNoGenericError`, `assertNoFalseSuccessClaim` (checks the reply against a list of success-claiming phrases whenever `mutationExecuted` is false — directly targets the false-success-claim bug above), `assertNoMutationYet`, `assertPlanningDraftInSync` (pending draft selections ↔ visible entities, a no-op for non-planning turns like hygiene), `assertPendingStateUnchanged`.
- `tests/agent-runtime-scripted-smoke.test.ts` — the 5 required scenarios (planning happy path, planning cancel path, no-stale-replyDraft, action-hygiene smoke, memory/Gmail/today smoke), each a plain TypeScript object literal. A `ScriptedTurn`'s `plan` field is plain JSON-serializable data, so a whole scenario's turn list could equally be authored as a JSON fixture and given only to `runScriptedScenario` — the `assert`/`assertAll` callbacks (being functions) stay in the TypeScript test file. One scenario (action hygiene) is run with the lower-level helpers directly instead of `runScriptedScenario`, since its own mocked args (which numbered index to snooze/archive) can only be known from the *preceding* turn's reply — `getActionItems` sorts by due date, not creation order — rather than being fixed data up front; everywhere else a scenario's plan is fully known ahead of time.

**Mocked vs. real LLM:** every turn in the 5 shipped scenarios sets an explicit `plan` (`AGENT_RUNTIME_PLANNER_MOCK_RESPONSE`), so the suite is fully deterministic and CI-safe with no network access or `OPENAI_API_KEY` required. A `ScriptedTurn` with no `plan` field lets the real planner run instead (the LLM if `OPENAI_API_KEY` is set locally, the deterministic heuristic fallback otherwise) — useful for an optional local run against the real model, which is the only way to catch a live-planner behavior gap like the "move the jobs to Friday" issue above (mocked tests, by construction, can only prove "if the LLM sends X, the code does Y correctly" — they cannot prove the LLM actually sends X).

**Tests:** 5 new scenario tests. Full suite: **275/275** (270 before this pass + 5 new).

**Validation:** `pnpm typecheck`, `pnpm build`, `pnpm test` (275/275), `git diff --check` — all clean. Zero production files changed — this pass is test-only.

**Next migration candidate:** unchanged — weekly review ("review my week"), with `apps/api/src/legacy/weekly-review-conversation.ts`'s `buildWeeklyReviewContext`/`generateAndSaveWeeklyReview` already non-legacy and reusable the same way `analyzeActionHygiene` and `buildNextWeekPlanContext`/`generateNextWeekPlanSuggestions` were. The scripted-eval harness above is directly reusable for it: a weekly-review scenario is just another `ScriptedScenario`.

## Weekly Review V3 Migration

**Goal:** make Agent Runtime v3 handle "review my week" (show a grounded review, then optionally save it) entirely in normal Telegram conversation, without falling back to legacy `/messages/process`, following the Migration Rule above.

**V3 capability map before this pass:** the tool catalog had no weekly-review tool at all. `legacy/weekly-review-conversation.ts` (734 lines) turned out to have **zero legacy/PendingAction coupling anywhere** — unlike planning's cluster (which had a real legacy-only opt-in-create reply parser) or hygiene's, every function in this file was already pure context-building, deterministic generation, formatting, or a direct `Memory`-row read/write with no stored confirmation state — the only thing making it "legacy" was its file location. Saving already existed: `generateAndSaveWeeklyReview` builds a draft and immediately persists it as a `Memory` row (`type: "pattern"`, `data.kind: "weekly_review"`), used by all three legacy weekly-review HTTP routes and by `/messages/process`'s own `weekly_review` intent — legacy has no "show without saving" mode anywhere; every legacy surface auto-saves on every generate (deduping via `getWeeklyReviewForWeek` + `updateMemory` instead of creating a duplicate for the same week).

**Reusable logic split into `apps/api/src/weekly-review/{context,review}.ts` (new, non-legacy):** since nothing in the original file was legacy-specific, effectively the whole thing moved verbatim (31 functions, diffed byte-for-byte against the original to confirm) — `context.ts` owns `buildWeeklyReviewContext` and its context-only helpers (goal progress, email-attention summary, action-relevance filtering, daily-loop counts); `review.ts` owns generation/saving/formatting (`generateAndSaveWeeklyReview`, `generateDeterministicWeeklyReview`, `maybeGenerateLlmWeeklyReview`, `getWeeklyReviewForWeek`/`getLatestWeeklyReview`, `formatWeeklyReview`, etc.) and imports two small helpers (`weeklyContextCounts`, `countType`) from `context.ts` — the only cross-file dependency, chosen to avoid a circular import (`context.ts`'s own `shouldPromptWeeklyReview` needed `getWeeklyReviewForWeek`, so it moved to `review.ts` alongside it instead). `apps/api/src/legacy/weekly-review-conversation.ts` is now a two-line `export *` re-export of both, so its existing callers (server.ts's three weekly-review routes, `legacy/messages-process.ts`, `apps/api/src/planning/next-week.ts`'s own `buildNextWeekPlanContext`) are unaffected.

**V3 operations added** (`apps/api/src/agent-runtime/tool-catalog.ts`):
- `weekly_review.start` (`mutates: false`, no confirmation): builds the week's context and a deterministic draft, shows it, and opens a pending save state on its own (via the same generic `ExecutedOperation.pendingOperationUpdate` mechanism next-week planning introduced) — safe to call again later in the conversation, since it always reflects real current data and never loses anything (unlike planning, weekly review has no editable draft to lose).
- `weekly_review.save` (`mutates: true`, no confirmation, but never planned by the LLM directly — same pattern as `planning.next_week_apply`): rebuilds the *same* week's context (from `weekStartLocalDate`/`timezone` pinned in the pending operation's own args, not a fresh "now") and calls the existing `generateAndSaveWeeklyReview` as-is — zero duplicated DB-mutation logic.

**A deliberate, minimal divergence from legacy's exact behavior:** legacy always saves immediately on every generate; V3 splits "show" from "save" into two explicit steps, matching the propose→confirm idiom next-week planning already established (and, unlike weekly review, next-week planning's *own* legacy behavior already had this same split for creating actions — so this is arguably more consistent with the product's overall design language than legacy weekly-review's own auto-save quirk). The task's `weekly_review.save` args intentionally hedge on this ("save the shown review only if current domain behavior supports this") — saving does exist, so the tool was built, but showing no longer implies saving.

**Reaching `weekly_review.save` safely:** exactly like `planning.next_week_apply`, the validator unconditionally rejects a direct LLM plan of `weekly_review.save` (`status: "invalid"`), so the only way it ever executes is via `finalizeDeterministicConfirmation` re-executing an already-stored pendingOperation. Unlike planning, though, the task's own example script uses an explicit phrase ("save this review") rather than a bare "yes" — so `"save this review"`, `"save the review"`, and `"save it"` were added to `runtime.ts`'s `CONFIRM_WHITELIST` alongside the existing "looks good" addition from the planning pass. The whitelist remains deliberately topic-agnostic (it already resolves against *whatever* is pending, not a specific tool), so this is a vocabulary extension, not a new mechanism.

**Session behavior:** `weekly_review.start`'s `pendingOperationUpdate` stores `weekStartLocalDate`/`timezone` (not the whole draft — nothing about the review needs index-based reference resolution the way planning's numbered items do, since there's no natural-language editing surface for a review). No new `AgentEntity` type was needed for the same reason.

**Grounding / no invented facts:** `weekly_review.start`'s executor never touches the LLM's `replyDraft` for the review's content — the entire multi-section reply (`formatWeeklyReviewDraftSummary`, new, `executor.ts`-local since its exact copy is V3-specific) is built from `generateDeterministicWeeklyReview`'s already-existing, already-safe output (the `WEEKLY_REVIEW_LLM_ENABLED`-gated LLM path, when enabled, is independently sandboxed by the pre-existing `isSafeWeeklyReviewDraft` check, unchanged). A week with no events/completed actions/overdue actions gets a distinctly shorter, honest reply (`formatThinWeeklyReviewSummary`, new) instead of the full template with empty sections — "Not much was logged this week..." — matching the task's explicit example shape.

**Files created:** `apps/api/src/weekly-review/{context,review}.ts`, `tests/agent-runtime-weekly-review.test.ts`. **Files changed:** `apps/api/src/legacy/weekly-review-conversation.ts` (trimmed to a two-line re-export, byte-identical behavior for everything it re-exports), `apps/api/src/agent-runtime/{tool-catalog,validator,executor,planner,runtime,response-composer}.ts`, `tests/agent-runtime-scripted-smoke.test.ts` (new scenario 6).

**What remains legacy, and why:** the three weekly-review HTTP routes and `/messages/process`'s `weekly_review` intent branch (`legacy/messages-process.ts`) are unchanged and still call the always-save legacy path directly — not deleted, since they're still reachable via Telegram slash commands and the legacy chat pipeline. Not provably unreachable.

**Tests:** `tests/agent-runtime-weekly-review.test.ts` (new, 9 tests) — "review my week" returns a grounded review matching exactly the seeded data (1 completed action, 1 workout, 1 overdue action — no invented counts); a thin/empty week gets the honest short-form reply instead of the full template; the pending save state is stored in session with the reviewed week pinned; "save this review" persists a `weekly_review` memory; "save this review" with nothing pending gets the fixed no-pending reply and saves nothing; "cancel" clears the pending state and saves nothing; a direct LLM plan of `weekly_review.save` is rejected (invalid) and mutates nothing; re-showing the review while its own pending save state is still open works (non-mutating, passes the firewall) rather than being blocked.
