## 2. Routing reality

**Default Telegram normal-text path (no env vars set):** `bot.on("message:text", ...)` (`apps/telegram-bot/src/index.ts:2065-2093`) calls `isLegacyTelegramChatEnabled()` (`agent-runtime-routing.ts:41-43`), which is `true` only when `TELEGRAM_AGENT_RUNTIME_V3_ENABLED === "false"` exactly. Unset, or set to anything else (including `"true"`), routes to `routeToAgentRuntimeV3(...)` (`index.ts:2077-2092`), which POSTs to `/agent/message`.

**`TELEGRAM_AGENT_RUNTIME_V3_ENABLED=true`:** identical to unset — no behavioral difference.

**`TELEGRAM_AGENT_RUNTIME_V3_ENABLED=false`:** `routeToLegacyMessageProcessor(ctx)` (`index.ts:1997-2063`) runs multi-intent → daily-checkin → ingest-text → `conversation/control` first, falling through to `POST /messages/process` (`index.ts:2054-2057`) only if nothing else claims the message.

**Is `/messages/process` still used by default Telegram traffic?** Yes, in three narrow places even with v3 enabled: the `/help` command calls it directly (`index.ts:136`); a pending-decision-with-trailing-command middleware calls it unconditionally regardless of the v3/legacy flag (`index.ts:55`); and `createManualActionFromCommand` (backing `/action`, `/todo`, `/add_action`) routes risky/gambling-sounding text through it specifically to reuse legacy's risk classifier (`index.ts:3818`) before creating a manual action from a slash command.

**Every slash command (105 registered, `index.ts:96-1965`)** calls a dedicated `/users/:id/...` API route, not `/agent/message` and (with the three exceptions above) not `/messages/process` either. Full one-line-per-command list is in the raw audit research; the pattern is consistent: memory/reflections/notifications/goals/integrations/actions/events/checkins/pending-actions each have their own route, several of which (`/actions/hygiene`, `/weekly-review*`, next-week-plan, Gmail email-rules) still call into `apps/api/src/legacy/*` server-side.

**Remaining live imports of `apps/api/src/legacy/*`** (all from `apps/api/src/server.ts` unless noted): `daily-conversation.ts` (onboarding routes + `messages-process.ts`), `messages-process.ts` (the `/messages/process` handler itself), `action-hygiene-conversation.ts` (`/actions/hygiene` route + `messages-process.ts`), `planning-conversation.ts` (next-week-plan route + `messages-process.ts`), `weekly-review-conversation.ts` (`/weekly-review*` route, `planning/next-week.ts`, `operator/attention.ts`, `messages-process.ts` — already a thin re-export shim from an earlier migration pass), `email-review-conversation.ts` (**only** `messages-process.ts` — the dedicated `/email-reviews*` routes use the separate, non-legacy `email-review-service.ts` instead), `gmail-conversation.ts` (Gmail email-rule slash routes + `messages-process.ts`). No legacy module is currently unreferenced by any live route.

## 4. Real-LLM local eval mode

CI stays fully deterministic — every scripted turn above sets an explicit `plan` field, which `mockPlan()` (`tests/helpers/agent-runtime-test-helpers.ts:34`) writes to `AGENT_RUNTIME_PLANNER_MOCK_RESPONSE`, so no network call happens and nothing depends on `OPENAI_API_KEY` in CI.

To run the same conversational shapes against the **real** LLM locally: write (or temporarily edit) a `ScriptedTurn` with **no `plan` field**. `runScriptedScenario` (`tests/helpers/agent-runtime-scripted-eval.ts:97-100`) only calls `mockPlan()` `if (turn.plan)` — omit it, and `planner.ts`'s real `planMessage` runs, which calls the OpenAI API when `OPENAI_API_KEY` is set in your shell, or falls back to the deterministic heuristic planner otherwise (`planner.ts:39-40`, `heuristicPlan`). Concretely:

```bash
export OPENAI_API_KEY=sk-...
export DATABASE_URL=postgresql://postgres:postgres@localhost:5432/alecto_ai?schema=public
pnpm exec tsx --test tests/agent-runtime-scripted-smoke.test.ts
```

Do this on a **copy** of a scenario (e.g. duplicate scenario 9's turns without their `plan` fields) rather than editing the checked-in file permanently — the checked-in scenarios must keep their `plan` fields so CI stays deterministic. No test file changes were needed to enable this; the hook already existed before this pass, just undocumented and unused.

## 5. Guardrails — the headline finding (historical — see §9 for the closed-gap follow-up)

`checkPolicyGuardrail` (`apps/api/src/agent-runtime/validator.ts:22-37`) is deliberately generic and data-driven: it only matches the user's own `UserOperatingProfile.knownTriggers`/`knownFailureModes` (both empty by default), and is checked in `runtime.ts:215-227` **before** the planner runs — if triggered, it returns a fixed "let's slow down and talk it through first" reply, plans and executes nothing.

Legacy has a **separate, more sophisticated, hard-coded mechanism** that V3 does not share at all: `packages/core/src/message-processing.ts:411-422` classifies `betting_intent`/`trading_intent` with an LLM-derived `riskState` (RED/ORANGE/GREEN) and, on RED, returns a hard "No. Hard stop." refusal — escalated further when the profile's distinct `gamblingGuardrails` field (default `"strict"`, escalatable to `"hard_guardian"`) is set. This is real, currently-live behavior — it's why `/action`/`/todo`/`/add_action` still route risky-sounding text through `/messages/process` even with v3 chat otherwise enabled (`apps/telegram-bot/src/index.ts:3818`).

**Net effect (at the time of the original audit):** a user typing "I want to bet €1000 because it feels safe" into normal V3 chat got **no special handling at all** unless they had already, separately, configured "bet"/"gambling" as a `knownTrigger` — something no default user would have done. **This is now closed — see §9.** The product decision was explicitly *not* to port legacy's `betting_intent`/`trading_intent` classifier; instead V3 gained a generic goal-conflict engine that treats "stop gambling" as just one instance of a user-authored goal, no different from "quit smoking" or "train 3x/week."

## 7. Early-user readiness verdict

**What Alecto can safely do now, in normal V3 chat:** save/recall memories; log progress and events; full action CRUD plus action-hygiene cleanup; the complete next-week planning propose → edit → confirm loop; weekly review show/save; Gmail connection status, rule listing/creation/pause/resume/archive; daily-loop settings show/change; itemized Gmail review triage (list → convert to action / reject by natural reference, as of §10); real, grounded active-goal listing (as of §11); nudge a genuinely empty user toward setting one real goal/guardrail anchor when they ask a broad operator/help question (as of §12); and, as of the §9 follow-up, intervene when a message conflicts with a goal or configured trigger the user has actually set. All of the above are tested (unit and/or scripted), require confirmation where they mutate meaningfully, and never fabricate facts in their grounded replies.

**What it should not promise yet:** creating/editing/deleting goals via chat (deliberately still unbuilt — §11 closes only the listing/honesty half, and the planner now says so explicitly rather than silently substituting a memory); onboarding/help guidance through normal chat beyond the one-line nudge (still slash/legacy-route only for anything deeper, which is fine, just don't imply chat covers it); any proactive/unprompted behavior (doesn't exist yet, by design — the §12 nudge is a reply to a question the user asked, never unprompted); any Gmail send/reply/label/mailbox mutation of any kind (still, deliberately, entirely unsupported); and protection at all for a risk the user has never named as a goal or trigger (§9) — the §12 nudge softens this by inviting the user to set one, but a user who ignores the nudge is still unprotected. Alecto does not, and by design should not, guess at unstated risks.

**Biggest risks for user testing:**
1. **Ambiguous Gmail-review references collapse to one generic clarification message.** `resolveGmailReviewRef` (§10) can't distinguish "zero matches" from "multiple matches" the way `gmail.rule.propose_update` does — both are safe (never mutate), but the wording is less specific than users may expect.
2. **No goal creation via chat at all, only an honest decline.** A user who says "create a goal to run a marathon" gets a clear, correct "not wired yet, use /create_goal" — this is the intended, safe behavior, not a bug, but it's worth confirming product is fine shipping this level of friction rather than wiring minimal creation next. The §12 nudge makes this friction more visible (it actively points empty users toward `/create_goal`), which raises the stakes slightly on this decision.
3. **The nudge's broad-question detection is a small, conservative allowlist, not a general "is this vague" classifier.** A genuinely empty user phrasing their first message unusually (not matching the ~8 patterns in `BROAD_OPERATOR_QUESTION_RE`) gets no nudge and falls straight to normal, potentially generic-feeling chat. This is the safe failure direction (never over-triggers into a specific flow), but means the nudge's real-world coverage depends on how closely users phrase things like the examples.

**Top 3 blockers before external users:**
1. Consider whether Gmail-review ambiguous/unknown-reference clarification wording (§10) is worth sharpening before wide release — currently safe but generic.
2. Decide whether minimal goal creation (reusing the already-clean `createGoal` service — see §11) is worth adding before external users, given how often "create a goal to X" is likely to come up once goal.list *and* the §12 nudge make goals a visible, actively-discussed part of the conversation.
3. Watch real usage of the §12 nudge's broad-question allowlist and expand it if users commonly phrase the same underlying "I don't know where to start" intent in ways it currently misses.

**Top 3 product improvements after baseline:** proactive operator behavior (the next planned phase — see §12, which this audit series was gating and now clears); minimal goal creation via chat, once product decides the honest-decline friction is worth removing; broader/smarter broad-question detection for the goal-anchor nudge if real usage shows the current allowlist is too narrow.

## 9. Follow-up: generic goal/guardrail engine (implemented)

A separate follow-up task closed §5's headline gap — deliberately **not** by porting legacy's hardcoded `betting_intent`/`trading_intent` classifier, but by building a domain-agnostic goal-conflict engine: `apps/api/src/agent-runtime/goal-guardrails.ts`. Product direction: Alecto should have no special-cased "gambling" or "financial" logic anywhere — a "stop gambling" goal, a "quit smoking" goal, and a "train 3x/week" goal are all just user-authored `Goal` rows, and the exact same code classifies conflicts against any of them.

**Design — two tiers, run before the planner (`runtime.ts`), replacing the old `checkPolicyGuardrail`:**
- **Tier 1 (deterministic, no LLM):** literal `UserOperatingProfile.knownTriggers`/`knownFailureModes` substring matching — the exact backward-compatible mechanism from before this pass, now living in `goal-guardrails.ts` instead of `validator.ts`. If a matching active goal shares vocabulary with the trigger phrase, the reply names that goal; otherwise it falls back to the same generic phrasing as before.
- **Tier 2 (LLM, optional/mockable, only runs when Tier 1 found nothing and the user has ≥1 active goal):** classifies the message against the user's own active goals **only** (id/title/why — nothing else, and the prompt explicitly forbids inventing a goal not in that list) into `none` / `soft_warn` / `hard_block` / `ask_clarification`, plus a `pattern` (`active_violation`, `avoidance`, `lapse_admission`). Mocked in tests via `AGENT_RUNTIME_GUARDRAIL_MOCK_RESPONSE` (mirrors the existing `AGENT_RUNTIME_PLANNER_MOCK_RESPONSE` pattern), so CI has zero `OPENAI_API_KEY` dependency — with neither a key nor a mock set, Tier 2 is skipped entirely and the turn defaults to `allow`, which is also why every pre-existing test that happens to seed goals (e.g. next-week-planning's tests) was completely unaffected by this change.
- A returned `goalId` is **never trusted blindly** — it's checked against the actual list of goals passed to the classifier; an invented or mismatched id collapses back to `allow` rather than blocking on a goal that doesn't exist (unit-tested explicitly).
- Reply text is a small set of deterministic templates parameterized by goal title + pattern + the user's own `directness` profile field (blunter phrasing at `directness >= 4`, softer otherwise) — never raw LLM prose, consistent with this codebase's established "LLM proposes, deterministic code composes the grounded reply" rule.
- On `hard_block`/`soft_warn`, the conflict is logged as a `risk_pattern` memory via the existing `createMemory`/`memory.create` mechanism (already read by `insights.ts`/`daily-review.ts`) — no new schema, and the LLM never touches the DB itself; the deterministic runtime code decides whether/what to log after classification.

**Examples now supported, all via the same code path:** "Stop gambling" + "I want to bet 1000 because it's safe" → hard block naming the goal. "Improve financial discipline" + an impulsive-purchase message → hard block naming that goal. "Find a new developer job" + browsing cars instead of applying → soft-warn accountability nudge. "Train 3x/week" + "I skipped gym again" → supportive lapse acknowledgment, not a hard stop. "I want to control my gambling impulses" against the same "Stop gambling" goal → correctly let through as supportive, not treated as the violation. No goal/trigger relevant → normal chat, untouched.

**Tests:** `tests/agent-runtime-goal-guardrails.test.ts` (new, 10 tests, covering exactly the A–H scenarios this follow-up task specified, plus invented-goalId and ask_clarification edge cases) + 3 rewritten/added scripted-smoke scenarios (13: cessation-goal hard-block + supportive follow-up + risk-memory logging; 14: pursuit-goal avoidance; 15: trigger-only path with no goal, confirming Tier 1 still works standalone) + one pre-existing test in `tests/agent-message.test.ts` updated in place, since it asserted the *old* "no mutation" guardrail behavior, which the new risk-logging behavior intentionally changes. Full suite: **325/325** (313 before this follow-up + 10 unit + 2 net-new scripted scenarios).

**Validation:** `pnpm typecheck` ✅ · `pnpm build` ✅ · `pnpm test` (325/325) ✅ · `git diff --check` ✅.

**Remaining, intentional gap:** if the user has no relevant goal or configured trigger, Alecto does not intervene — by design, per explicit product direction ("Alecto should not pretend to enforce a goal the user never set"). This means guardrail coverage is only as good as the goals/triggers a user has actually set, which is a meaningfully different (and more honest) safety posture than legacy's blanket gambling/trading detection, but is not a substitute for it for a user who hasn't configured anything yet — see the updated readiness verdict (§7) for the resulting risk and blocker.

## 10. Follow-up: Gmail review triage reachable via normal chat (implemented)

Closes §1's other originally-partial capability: `gmail.review.list`/`reject`/`to_action` were already fully wired mechanically but unreachable by a real LLM turn. No Gmail OAuth/callback/sync/provider code was touched, and no send/reply/label capability was added — this pass only makes the existing, already-DB-only mutations (reject/to_action) actually reachable through normal chat.

**Planner guidance:** `planner.ts`'s system prompt now has an explicit bullet (previously zero) teaching when to plan all three tools, covering "what emails need my attention?", "what Gmail reviews are waiting?", "show pending email reviews", "anything important in Gmail?" (→ `gmail.review.list`), "turn the recruiter one into a task"/"make the recruiter email an action"/"create an action from the email about X" (→ `gmail.review.to_action`), and "reject/ignore the Endesa one" (→ `gmail.review.reject`) — explicit that both mutating tools reference the most recently shown list by `index` or `ref`, never inventing a `reviewId`.

**Itemized list:** `gmail.review.list`'s summary changed from a bare count ("N email review(s).") to a numbered, grounded list (`apps/api/src/email-reviews/email-review-service.ts`'s new `formatGmailReviewListForChat`/`gmailReviewChatLabel`/`gmailReviewChatDescription`) — each line is the review's own real subject (or sanitized sender, or tracking-rule name as a last resort) plus a safely truncated snippet/evidence excerpt, never an invented summary. Reuses the same non-legacy service module the dedicated `/email-reviews` HTTP route already depends on (`extractSafeSenderLabel`/`truncatePlainText` for PII-safety and length limits), rather than duplicating formatting logic. Each listed item is stored as a `gmail_review`-type visible entity with a 1-based `index`, matching the pattern established for action-hygiene lists.

**Follow-up resolution:** `gmail.review.reject`/`gmail.review.to_action` gained optional `index`/`ref` args (alongside the pre-existing `reviewId`, now optional). A new `resolveGmailReviewRef` in `validator.ts` resolves these **synchronously against `context.session.visibleEntities`** — never a fresh DB lookup (unlike `gmail.rule.propose_update`, since a review's identity here is only meaningful in the context of "the list you just showed me") and never hidden LLM memory. An explicit numeric `index` always wins; free-text `ref` is resolved via `selectEmailRuleCandidate` (`apps/api/src/conversation/email-rule-selection.ts`) — the exact same exact-name/token-overlap/ordinal matcher legacy's own numbered Gmail-rule-selection flow already relies on, reused as-is rather than writing a third near-duplicate fuzzy matcher. Zero or multiple matches both resolve to `needs_clarification` with no mutation; a returned candidate id is always a real visible entity's id, never invented. No review list shown yet in the conversation also asks for clarification rather than guessing.

## 13. V3 Proactive Operator MVP (decision/preview layer — implemented)

The first proactive layer for Agent Runtime v3: a pure, callable decision module plus a preview-only API route. **Actual scheduled sending is deliberately not wired this pass** — this is explicitly the "first milestone: preview decisions are correct" the task scoped, not a live feature.

**Existing infrastructure mapped first (nothing here duplicates it):** `apps/worker` already runs a full proactive system — a `setInterval` tick loop (`apps/worker/src/index.ts`) that already sends real Telegram messages on a schedule for legacy daily-loop start-day/end-day, check-ins, insights, action reminders, and Gmail sync notifications, all via a raw `sendTelegramMessage` HTTP call to the Telegram Bot API (no grammy/apps/telegram-bot involvement) and deduped via `NotificationLog` (`userId+type+sentForDate`, calendar-day granularity) or `ActionItemReminderLog` (action-item-specific, not general-purpose). Crucially, **all of that is legacy-content-driven** (calls `/daily-loop/start-day` etc.) and entirely disconnected from Agent Runtime v3's tool catalog/planner/executor — V3 itself had zero proactive code path before this pass, confirmed by this same audit's earlier findings. `apps/api/src/operator/attention.ts`'s `buildOperatorAttentionState`/`generateDailyOperatorBrief` is the closest existing "what does the user need to know" engine, but it's pull-based (used by `/today`/`/operator-attention`) with no send logic of its own.

**What was built:** `apps/api/src/operator/proactive.ts` — `decideProactiveOperatorMessage(input)`, a pure function (no DB reads, no sends) that takes an already-loaded `ContextBundle` (the exact same shape `agent-runtime/context-loader.ts` builds for every normal chat turn — reused as-is, not reinvented), the user's `NotificationSettings`, the current time, and which dedupe keys/how many proactive sends already happened today (both computed by the caller, not the module itself). Returns either `{decision: "no_message", reason}` or a fully-formed `{decision: "proposed_message", type, title, message, reasons, suggestedReplies, dedupeKey, priority, safeToSend}`. Wired to exactly one integration point: `GET /users/:userId/operator/proactive/preview` (`apps/api/src/routes/agent.ts`) — loads context via the unmodified `loadContext`, checks `hasNotificationLog` (existing, unmodified DB function) for each candidate dedupe key, and returns the decision. **Never calls `createNotificationLog` or sends anything** — a repeated preview call shows the same candidate every time, which is correct for a preview-only endpoint.

**Three proactive moments, in priority order (1 highest) when more than one is simultaneously eligible — only one is ever returned per call:**
1. **`morning_brief`** — triggers within ±30 minutes of `morningTimeMinutes`. Grounded top-3 open actions (ranked by priority then due date, never invented), one "skip X" line for a genuinely lower-priority deferred item, and one "watch out" line only when a real `risk_pattern` memory (from the goal-guardrail engine, §9) was logged that same local day. With zero active goals AND zero open actions, reuses the exact goal-anchor-nudge text (`runtime.ts`'s `GOAL_ANCHOR_NUDGE_REPLY`, now exported) rather than sending an empty brief.
2. **`evening_checkin`** — triggers within ±30 minutes of `eveningTimeMinutes`. Only asks about active goals that have a real `targetMetrics[].eventType` AND no matching event logged that local day (checked against `context.recentEvents`) — capped at 2 goals per message, and returns `no_message` entirely if every trackable goal already has a signal today (no nagging).
3. **`gmail_nudge`** — fires whenever `context.gmailReviews` is non-empty and the current time falls between the user's morning/evening bounds (the quiet-hours proxy — see below). Picks the top pending review, summarized via the exact same `gmailReviewChatLabel`/`gmailReviewChatDescription` helpers the Gmail-review-triage pass (§10) already built — safely truncated, sender-sanitized, no raw email address ever included. Deduped **per review** (`v3_gmail_nudge:<reviewId>`), not just per day, so a new review later in the day still gets its own nudge.

**Anti-spam / quiet hours:** no dedicated quiet-hours field exists anywhere in the schema (confirmed during infra mapping) — daily-loop settings are the available proxy, used two ways: `dailyLoopEnabled: false` suppresses every proactive message outright (the clearest available "don't nudge me" signal), and `gmail_nudge` is bounded to the user's own configured morning-to-evening window so it never fires overnight. The 1–3/day cap is a single check — `sentCountToday >= 3` returns `no_message` before any candidate is even built, so it's a hard global cap rather than a "higher priority overrides the cap" mechanism (a deliberate simplification, noted below). Dedup reuses `NotificationLog` exactly as-is, no schema changes — `morning_brief`/`evening_checkin` use fixed per-day keys, `gmail_nudge` encodes the review id into the `type` string for per-item dedup within the same generic table.

**Tests:** `tests/agent-runtime-proactive.test.ts` (new, 11 tests, through the preview route end-to-end) covering all 10 specified unit scenarios (grounded morning brief, goal-anchor fallback, no invented facts, evening check-in asking about untracked signals, no nagging once logged, safe Gmail summary, no-reviews-no-nudge, duplicate-dedupe-key suppression, quiet-hours/daily-loop-disabled suppression, daily-cap suppression) plus 2 new scripted-smoke scenarios (17: preview an evening check-in → user replies with both signals → both events logged via **existing, unmodified** event-logging tools; 18: preview a Gmail nudge → user replies "turn it into a task" → **existing, unmodified** Gmail review-to-action path creates the grounded action) — proving the proactive layer's job is only to decide *whether* to nudge, never to reimplement reply-handling. Full suite: **364/364** (351 before this pass + 11 unit tests + 2 scripted scenarios).

**Validation:** `pnpm typecheck` ✅ · `pnpm build` ✅ · `pnpm test` (364/364) ✅ · `git diff --check` ✅.

**What remains before enabling for real users:**
1. **Actual sending is not wired.** No cron/worker integration calls `decideProactiveOperatorMessage` and no code path calls `sendTelegramMessage`/`createNotificationLog` for a V3 proactive message — by design, per this task's "prefer a callable decision module first" / "do not send real messages automatically" rules. Wiring this means either extending `apps/worker`'s existing tick loop to also call the preview logic (and, on `proposed_message`, actually send + log) behind an explicit enable flag, or a new dedicated proactive worker tick — a genuinely separate, later decision.
2. **Session-entity delivery isn't built.** For a real Gmail-nudge send to support a bare "turn it into a task" reply (no "the recruiter one" qualifier), delivery would also need to record the referenced review as a visible session entity — scenario 18 simulates this directly via the DB to test the reply-handling half honestly, but no code does this yet.
3. **The daily cap is a hard global cutoff, not priority-aware.** "Do not send a lower-priority nudge if a higher-priority one already exists" is satisfied within a single decision call (only the single highest-priority eligible candidate is ever returned), but the cross-call 1–3/day cap doesn't distinguish "3 gmail nudges already sent, block everything" from "a much more important morning brief is now also eligible" — worth revisiting once real sending exists and this matters in practice.

## 15. User-level proactive consent layer (product correction — implemented)

Product correction: `PROACTIVE_OPERATOR_DELIVERY_ENABLED`/`PROACTIVE_OPERATOR_ALLOWLIST` are — and were always meant to be — **developer rollout controls**, not the product UX. Final Alecto should not require an env variable to decide whether to nudge a real user. This pass adds the actual product-level control: three new, dedicated, per-user `NotificationSettings` booleans — `morningBriefEnabled`, `eveningCheckinEnabled`, `gmailNudgeEnabled` — all defaulting to `false` (opt-in, never on by default), plus V3 conversational tools to view/change them, plus the rule that morning-brief delivery now requires this consent in addition to the existing env/allowlist gates.

**Settings model chosen, and why not `dailyLoopEnabled`:** mapping confirmed `dailyLoopEnabled` is a genuinely different, older feature — it (and `morningTimeMinutes`/`eveningTimeMinutes`, which stay shared/reused since they're just "what time is your morning/evening") gates the legacy `/daily-loop/start-day`|`end-day` messages, not V3's proactive engine. Reusing it for the new consent would have been exactly the "overload a vague setting" the task warned against. The three new fields live on the same `NotificationSettings` table (Prisma migration `20260819224352_add_proactive_operator_settings`, purely additive: three `Boolean NOT NULL DEFAULT false` columns, zero data loss risk) rather than a new model, matching how every other notification toggle (`dailyCheckinEnabled`, `dailyInsightEnabled`, `weeklyInsightEnabled`, `dailyLoopEnabled` itself) already lives there. `packages/core/src/notifications.ts`'s `NotificationSettingsSchema`/`UpdateNotificationSettingsInputSchema` and `packages/db/src/index.ts`'s `toNotificationSettings` mapping were updated in lockstep.

**Two independent gates, deliberately separate layers:**
- `decideProactiveOperatorMessage` (`apps/api/src/operator/proactive.ts`) is **completely unchanged** — still a pure content-decision module, still gated on `dailyLoopEnabled` and the existing dedupe/cap/quiet-hours logic exactly as before. It stays unaware of env flags or the new per-user consent fields; every one of §13's existing tests passes unmodified, by design.
- A new `apps/api/src/operator/proactive-eligibility.ts` (`evaluateProactiveEligibility`) layers real send-eligibility on top, independently checking `PROACTIVE_OPERATOR_DELIVERY_ENABLED`, `PROACTIVE_OPERATOR_ALLOWLIST`, and — new — the decision's own `type` against the matching consent field (`morning_brief`→`morningBriefEnabled`, etc.). Used by the preview route to report `wouldSend`/`blockedBy` (`delivery_disabled` | `not_allowlisted` | `user_not_opted_in` | `quiet_hours` | `dedupe` | `no_candidate` — the last three map from the decision module's own `no_message` reasons). This is informational for preview; it is not the sole authority a real send relies on.
- `apps/worker/src/v3-proactive-delivery.ts`'s actual send gate independently re-checks `morningBriefEnabled` itself (alongside its existing `dailyLoopEnabled`/allowlist/telegramUserId checks) before ever calling `sendTelegramMessage` — defense in depth, not reliant on the preview route's eligibility field being consulted correctly by every future caller.

Both `PROACTIVE_OPERATOR_DELIVERY_ENABLED`/`PROACTIVE_OPERATOR_ALLOWLIST` env-reading functions were extracted from `apps/worker` into `packages/core/src/proactive-operator-env.ts` so `apps/api`'s preview route and `apps/worker`'s delivery code read the exact same two env vars the exact same way, without duplicating the parsing logic.

**V3 conversational controls:** three new tools, mirroring `daily_loop.settings_*`'s established propose→confirm shape exactly — `proactive.settings_show` (read-only), `proactive.settings_propose_update` (opens a pending confirmation, never mutates by itself), `proactive.settings_apply_update` (mutates, but the validator rejects it outright if the LLM ever tries to plan it directly — only the exact confirm whitelist re-executing an already-stored pending operation can reach it, identical to every other settings-apply tool in this codebase). ## 16. Settings/delivery UX bugs from real Telegram testing (bug-fix pass — implemented)

Real Telegram testing of §15's consent layer surfaced five problems: (1) "setup a morning brief at 01:06" only set the time via the legacy `daily_loop.settings_propose_update` tool — it never turned `morningBriefEnabled` on, so nothing was ever scheduled to send, despite the bot replying "Done"; (2) "what proactive messages are on?" showed on/off but not the scheduled time; (3) there was no way to ask "why didn't I get my morning brief?" and get a real answer; (4) asking that question hit the generic settings-comparison no-op reply ("That's already how it's set"); (5) "on" in the settings display conflated per-user opt-in with actual deliverability, which also depends on `PROACTIVE_OPERATOR_DELIVERY_ENABLED`, the allowlist, whether the worker process is running, `dailyLoopEnabled`, the time window, and `NotificationLog` dedupe — none of which the user can see.

**Root cause:** two tools independently, and only partially, controlled the same `NotificationSettings` row — `daily_loop.settings_propose_update` could set `morningTimeMinutes` but not `morningBriefEnabled`; `proactive.settings_propose_update` (§15) could set `morningBriefEnabled` but had no time-setting capability at all. Neither tool could express "turn on AND schedule" as one action, so the planner picked whichever tool matched the surface phrasing and silently dropped the other half of the user's intent.

**Fix — one tool now owns both concerns:** `proactive.settings_propose_update`/`settings_apply_update` gained `morningTimeText`/`eveningTimeText` (propose) and `morningTimeMinutes`/`eveningTimeMinutes` (apply) arguments, alongside the existing enable/disable booleans. Reply yes to confirm or cancel." / "Done — the morning brief is now on at 09:00." — rather than two disjointed phrases. A time-only request while the moment is off ("move morning brief to 9") still only changes the time, but the reply now says so explicitly: "Done — the morning brief time is now 09:00, but the morning brief is still off." `proactive.settings_show`'s summary now includes the scheduled time when a moment is on ("Morning brief: on, around 09:00"). The legacy `daily_loop.settings_*` tools are unchanged.

**New diagnostic tool — `proactive.diagnose_morning_brief`:** answers "why didn't I get my morning brief?" / "it's 9 and no morning brief" / "where is my morning brief?" with a single, most-specific, grounded status via `getProactiveDeliveryStatus` (`apps/api/src/operator/proactive-eligibility.ts`), instead of the generic settings-comparison reply. Statuses, checked in order: `delivery_disabled` (env kill switch off) → `user_not_allowlisted` (allowlist set but excludes this user — `missing_allowlist` is kept in the type for vocabulary completeness but is not currently reachable, since an unset allowlist means "open to everyone," not a blocker) → `user_not_opted_in` (the actual per-user consent is off) → `daily_loop_disabled` (the older feature's own gate, still checked by the content-decision module) → `outside_morning_window` → `duplicate_dedupe_key` (already sent today) → `no_candidate` (decision module found nothing grounded to send) → `eligible` ("Settings look eligible — check whether the worker process was running... and whether Telegram delivery failed"). `getProactiveDeliveryStatus` reuses `decideProactiveOperatorMessage` and its exported time-window primitives (`isWithinWindow`, `minutesOfDayInTimezone`, `TIME_TRIGGER_WINDOW_MINUTES`) directly rather than reimplementing them, so it can't drift out of sync with either the content-decision module or `apps/worker`'s own send gate. See the doc comment in `apps/worker/src/v3-proactive-delivery.ts` for exactly how its exact-minute tick trigger and this diagnostic's ±window check relate (same underlying gates, deliberately different time-matching semantics for a continuously-ticking sender vs. a point-in-time explanation) — true single-function sharing isn't possible across the `apps/api`/`apps/worker` package boundary (HTTP-only, no shared source imports), so drift is avoided by both sides importing the same low-level primitives from `proactive.ts`, not by literal code identity.

**Preview route:** `GET /users/:userId/operator/proactive/preview` now additionally reports `scheduledTime` (the morning brief's formatted time, when one is proposed) and `optIn` (the three raw per-user consent booleans), alongside the existing `wouldSend`/`blockedBy`. Purely additive — still computes and returns without writing `NotificationLog` or any other DB state.

**Tests:** 3 new tests in `tests/agent-runtime-proactive-settings.test.ts` (fused enable+time propose/apply, time-only-while-off with the correct caveat text, settings_show includes the scheduled time), a new `tests/agent-runtime-proactive-diagnosis.test.ts` (6 tests — one per reachable status: `delivery_disabled`, `user_not_allowlisted`, `user_not_opted_in`, `daily_loop_disabled`, `duplicate_dedupe_key`, `eligible`), 2 new tests in `tests/agent-runtime-proactive-eligibility.test.ts` (preview reports `scheduledTime`/`optIn`; preview still writes nothing). One pre-existing eligibility test's strict `deepEqual` was loosened to check `wouldSend`/`blockedBy` individually now that the response carries additional fields. Full suite: **401/401** (391 before this pass + 3 + 6 + 2 - 1 test renumbered, net +10 new tests).

## 18. Legacy daily-loop vs V3 proactive morning delivery — ownership and duplicate-send prevention (implemented)

§17's audit traced a real morning message to the legacy daily-loop sender, not V3. That raised the actual open question this section closes: **both systems are wired into the same worker tick, driven by the same `NotificationSettings` row, and nothing stopped both from sending a real Telegram message to the same user in the same tick** once V3 real delivery is ever turned on. This had not yet been exercised in practice only because `PROACTIVE_OPERATOR_DELIVERY_ENABLED` defaults to `false`.

**System A — legacy daily loop:**
- Entry point: `GET /users/:userId/daily-loop/start-day` (`apps/api/src/server.ts`), content built by `apps/api/src/operator/attention.ts`'s `buildStartDayMessage` (the "Today - ... / First move: ... / Guardrail: ... / Reply naturally with updates." format — a self-documented **"Legacy operator-attention/daily-brief cluster, extracted from server.ts"**).

- Settings used: `dailyLoopEnabled` (must be `true`) and `morningTimeMinutes` (exact-minute match against local time each tick).
- NotificationLog key: `daily_loop_morning` (written both by the route itself, when called with `markSent=true`, and redundantly re-attempted by the worker after a successful send — a pre-existing quirk, unchanged by this pass, where the worker's own write always fails silently as a duplicate).
- Gates: `telegramUserId` + `dailyLoopEnabled` + exact `morningTimeMinutes` match. `morningBriefEnabled` (V3's own field) does **not** gate this system at all, by itself.

**System B — V3 proactive morning brief:**
- Preview route: `GET /users/:userId/operator/proactive/preview` (`apps/api/src/routes/agent.ts`), content built by `apps/api/src/operator/proactive.ts`'s `buildMorningBrief` (the "Morning. - Settings used: `dailyLoopEnabled` (also required — a deliberate, pre-existing design choice: dailyLoopEnabled is treated as the shared "is any daily messaging on" master switch), `morningBriefEnabled` (V3's own per-user consent), `morningTimeMinutes` (the exact same field System A uses — both systems schedule off one shared time).
- NotificationLog key: `v3_morning_brief`.
- Gates: `telegramUserId` + `dailyLoopEnabled` + `morningBriefEnabled` + exact `morningTimeMinutes` match + `PROACTIVE_OPERATOR_DELIVERY_ENABLED` (env, developer rollout control, default `false`) + the allowlist (env, developer rollout control, default open when unset — but the master flag being off already blocks everyone).

**Exact overlap:** both systems key off the identical `dailyLoopEnabled` + `morningTimeMinutes` pair, in the identical worker tick, for the identical user — the only settings-level differentiator is `morningBriefEnabled`, and before this pass NOTHING read that field to suppress System A. Different content, different NotificationLog keys, both real sends once both are live for a user.

**Ownership decision:** going forward, "morning brief" in normal V3 chat means the V3 proactive morning brief (System B) — never the legacy daily-loop start-day message. `daily_loop.*` tools/settings are only reached by explicit daily-loop language ("daily loop", "daily review", "start-day"/"end-day"). **Duplicate-send prevention — chosen design: V3 suppresses legacy, not preview-only.** `runLegacyDailyLoopMorningBriefs` now skips sending (with a clear log line) whenever V3 is **actually configured to own delivery for that user**: `morningBriefEnabled === true` AND `PROACTIVE_OPERATOR_DELIVERY_ENABLED === true` AND the user is allowlisted — the exact same three conditions `runV3ProactiveMorningBriefs` itself checks, read via the same `proactiveOperatorDeliveryEnabledFromEnv`/`proactiveOperatorAllowlistFromEnv` from `@operator-agent/core`. Only when V3 is genuinely about to send does legacy step aside. Order between the two worker calls doesn't matter: legacy's check is purely configuration-based (never "did V3 actually produce content this tick"), so there's no race between them.

**Is V3 proactive real delivery actually wired?** Yes, exactly as before this pass — for `morning_brief` only, off by default behind `PROACTIVE_OPERATOR_DELIVERY_ENABLED` (§14). This pass did not change who V3 sends to, only ensured legacy steps aside when it does.

## 19. Simplified rollout controls for the solo/dev phase — optional, normalized allowlist (implemented)

§18's live debugging ended with the real root cause: `PROACTIVE_OPERATOR_ALLOWLIST=520894688` didn't match the internal userId `telegram:520894688` — a config format mismatch, not a code bug. But it exposed a real ergonomics problem: with no real users yet, requiring an exact-format allowlist entry for every test is friction that doesn't buy any real safety, and it's what caused the confusion in the first place.

**Rollout control model going forward:**
- `PROACTIVE_OPERATOR_DELIVERY_ENABLED` — unchanged, still the **required** global kill switch. No real send happens without it.
- Per-user opt-in (`morningBriefEnabled` etc.) — unchanged, still the **required**, real product consent, and now the *main* safety layer for this phase.
- `PROACTIVE_OPERATOR_ALLOWLIST` — now explicitly **optional**. Unset/empty means "no further restriction" (every opted-in user is eligible once the kill switch is on) — this was actually already the implemented behavior (`proactiveOperatorAllowlistFromEnv()` always returned `() => true` for an empty value), so no behavior change there; what changed is the *ergonomics* around it.

**Allowlist normalization** (`packages/core/src/proactive-operator-env.ts`, new `normalizeProactiveAllowlistId`): a bare Telegram numeric id (`520894688`) and the full internal form (`telegram:520894688`) are now both accepted and normalized to the same canonical value before matching — a developer configuring this never has to know the internal userId format. Applies to every comma-separated entry, with whitespace trimmed. New `proactiveOperatorAllowlistActiveFromEnv()` reports whether an allowlist is configured at all, separately from whether a specific user matches it — needed because "no allowlist" and "allowlist active but excludes you" are different facts that were previously collapsed into one boolean.

**Diagnostics — dead status removed, "eligible" enriched.** The `missing_allowlist` status (already documented as unreachable — an empty allowlist never blocked delivery even before this pass) was removed from `ProactiveDeliveryStatus` entirely; it served no purpose and its presence in the vocabulary risked implying a missing allowlist is an error condition, which it deliberately isn't. **Preview route additions** (`GET /users/:userId/operator/proactive/preview`): `eligibility` now additionally reports `deliveryEnabled`, `allowlistActive`, and `allowlistMatched` (only present when `allowlistActive` is true — otherwise it's not a meaningful answer), alongside the existing `wouldSend`/`blockedBy`/`scheduledTime`/`optIn`.

The existing per-tick, per-user skip logging (added in §18, unchanged in shape here) automatically benefits from the same normalization, so a bare numeric id in the allowlist is now correctly recognized as a match rather than logged as a mismatch.

**Not touched:** `evening_checkin`/`gmail_nudge` remain preview-only (no change to real-delivery scope); legacy daily-loop is untouched and still defers exactly as §18 established; Telegram chat routing, slash commands, and `/messages/process` are all untouched.

## 21. Adaptive Goal Creation / Goal Operating Plan MVP (implemented)

Product correction to §20: "future goals can reuse this with registry/template/enum additions per domain" is not good enough long-term — Alecto must handle an arbitrary user goal ("I want to drink more tea," "I want to call my grandmother every Sunday," "I want to stop scrolling in bed") without a developer adding a new template or EventType every time. This section closes that.

**Task 1 finding — the key architectural fact:** `Goal.targetMetrics` is a Postgres `Json?` column (`packages/db/prisma/schema.prisma`), not a set of typed columns — adding a new field to what it can hold needs **zero database migration**, only a Zod schema addition. `GoalMetricSchema.eventType` (`packages/core/src/goals.ts`) was already `z.string().optional()` — an unconstrained string, not `z.enum(EventTypeSchema)` — so a goal's own metrics were never actually locked to the registry at the schema level. What IS constrained to the ~90-value `EventTypeSchema` enum is `StoredEvent.type` — but only via TypeScript's static typing at specific call sites (`CreateEventInput.type: StoredEvent["type"]`); the underlying `Event.type` Postgres column is a plain `String`, and `createEvent`/`createEvents` (`packages/db/src/index.ts`) perform no runtime `.parse()` against the enum before writing. The registry exists as an **application-layer convention for well-known, structured signals**, not a database-level constraint — and it already has a generic escape hatch, `custom.goal_progress_logged`, with a free-form `data` JSON field, previously used by `event.log_custom_progress`.

**Minimal additive change chosen:** one new optional field on `GoalMetricSchema` — `signalKey: z.string().optional()`. A metric sets either `eventType` (a real registry type — job-search's existing career.* signals, unchanged) or `signalKey` (a free-form per-goal discriminator like `"tea_cups_drunk"`, `"called_grandmother"`), never both. Custom-signal evidence is stored as a real event with `type: "custom.goal_progress_logged"` and `data.signalKey` set to the metric's own key — reusing the exact event type `event.log_custom_progress` already wrote to, so nothing about the Event model, the registry, or the DB schema changed at all.

**New primitives** (`packages/core/src/goal-evidence.ts`): `CUSTOM_SIGNAL_EVENT_TYPE` (the shared constant), `findGoalsForSignalKey` (the signalKey-matching sibling of §20's `findGoalsForEventType`), `countEvidenceForMetric(metric, events)` (counts evidence for ONE metric regardless of which kind it is — the single place that needs to know both metric shapes exist; every caller just asks "how much evidence for this metric").

**New V3 tools:**
- `goal.create_propose` (`mutates: false`) — the LLM proposes a full custom operating plan grounded in what the user said: title, free-text category (never a fixed enum), why if stated, optional successCriteria, 1-3 signals (each an LLM-invented short snake_case key + human label — e.g. `tea_cups_drunk` / "cups of tea drunk"), an optional check-in suggestion, an optional integration hint (only when a real integration is genuinely relevant — never claims monitoring that isn't wired up), and 0-3 first actions. Deterministically formatted into the exact "Goal: ... / Signals: ... / Want me to create this goal?" shape (`formatGoalPlanProposal`) — the LLM's own args are structured, never raw prose shown directly. Opens a `pendingOperationUpdate` targeting `goal.create_apply`, exactly like every other propose→confirm flow in this codebase (`daily_loop.settings_propose_update`, `proactive.settings_propose_update`, ...).
- `goal.create_apply` (internal-only) — added to `validator.ts`'s "never planned directly by the LLM" rejection list, the same pattern as `daily_loop.settings_apply_update`/`proactive.settings_apply_update`/`gmail.rule.apply_update`. On confirmation: calls the existing, unmodified `createGoal` (no new DB function needed — `targetMetrics`/`checkInConfig` were already accepted args) with the proposed signals turned into `GoalMetric`s (`signalKey` set to each signal's own key) and the check-in turned into one `checkInConfig` entry; creates any proposed first actions linked to the new goal via `goalId`. A duplicate active goal title is reported honestly, never silently re-created.
- `goal.tracking_show` — shows what's actually CONFIGURED for a goal (its real signal keys, so a follow-up `goal.log_evidence` call can be correct rather than guessed) — distinct from `goal.status`, which shows progress.
- `goal.log_evidence` (§20, widened) — now accepts `signalKey` as an alternative to the fixed `eventType` enum. A `signalKey` is **only ever trusted when an active goal already declared it** in its own `targetMetrics` (checked deterministically in the executor via `findGoalsForSignalKey`, the same "LLM proposes, executor verifies against real data" pattern used everywhere else in this codebase) — an unrecognized key is refused with a clear message, never silently logged. **`eventType`'s fixed 5-value career enum was widened further in §22** to any real registered event type, since it turned out to block logging evidence for non-career template goals (e.g. a "Read more" goal's `learning.reading_session_completed` metric) entirely.
- `goal.status` (§20) — its per-metric counting was reworked to iterate the goal's own `targetMetrics` via `countEvidenceForMetric` instead of raw event types, so registry-backed and custom signals are counted and labeled (using the metric's own `label`, set at creation) through one unified code path.
- `action.create` — unchanged from §20 (already auto-links to a matching active goal).

**Confidence/safety rules honored:** the LLM never writes a DB record directly — `goal.create_apply` only ever runs via the deterministic confirm whitelist re-executing a `pendingOperation` the executor itself stored; a `goalRef`/`signalKey` the LLM supplies is always re-verified against real `context.activeGoals` data before anything happens, never trusted blindly; a genuinely vague statement ("I want to be better") is guided toward `clarification.ask`, never a fabricated plan; an ambiguous-but-not-quite-a-goal statement can still fall back to `memory.create(type: "goal_context")` with an explicit "not a tracked goal yet" reply, exactly as before. `formatGoalListForChat`'s and `GOAL_ANCHOR_NUDGE_REPLY`'s closing lines (previously "goal creation through chat isn't wired yet, use /create_goal") were updated — creation now works through chat; only editing/deleting an *existing* goal still isn't wired.

**Existing goal evidence loop still works, unchanged in shape:** every §20 test still passes; job-search's `career.*` signals go through the exact same `goal.log_evidence`/`goal.status` tools, now just sharing them with custom signals rather than needing separate code paths.

## 22. Goal Reference Fix — specific-goal resolution, evidence/status consistency, reading-goal plan quality (implemented)

A real Telegram smoke test of §21 surfaced a bug once a user has more than one active goal: creating "Finish reading Nietzsche book" while an older, generic "Read more" goal was already active, then asking "show tracking for reading niezsche book" (a typo of "Nietzsche"), returned **"Read more"**, not the goal actually named. The same mismatch hit `goal.status` ("how is my nitzche book goal goin"), and logging "read 5 minutes" produced a confident-sounding reply ("I've logged that you read for 5 minutes on your Nietzsche book") that later turned out not to be counted by `goal.status` at all.

**Root cause 1 — wrong matcher for the job.** `goal.status`/`goal.tracking_show`'s `goalRef` resolution (§20) reused `goal-linking.ts`'s `inferGoalLinkForAction` — a matcher deliberately built for a *different* question ("which goal's general DOMAIN does this new ACTION belong to"), with coarse category buckets (any reading-flavored text matches ANY "learning"-category goal at a fixed high confidence) and zero typo tolerance. Naming a *specific* goal needs the opposite bias: a specific, exactly-relevant match must always beat a generic, same-category one, and a proper noun a user is likely to misspell needs some fuzz tolerance. Reusing the action-linking matcher meant a generic category match structurally could — and did — outscore (and outright block, given the typo) the correctly-named goal.

**Root cause 2 — the false "logged" reply.** `goal.log_evidence`'s `eventType` was a hardcoded 5-value, career-only Zod enum (§20). A template-based goal like "Read more" declares its real metric as `eventType: "learning.reading_session_completed"` (`packages/core/src/goal-templates.ts`) — a value the old enum could never accept, so there was no valid way to log against it through `goal.log_evidence` at all. `response-composer.ts`'s `composeReply` trusts a mutating tool's *own* LLM-authored `replyDraft` whenever the tool call succeeds (deliberately, to avoid duplicating a deterministic summary) — so when the planner fell back to the untargeted `event.log_custom_progress` tool instead (which mutates successfully but is never linked to any goal's metric), its confident replyDraft was shown verbatim, even though nothing about the log was actually attributable to any goal or counted by `goal.status` afterward. The fix closes the capability gap that caused the fallback in the first place, rather than changing `composeReply`'s trust rule (which is correct and used throughout the codebase).

**Fix — a dedicated goal-reference resolver, kept separate from goal-linking.ts:**
- New `packages/core/src/goal-reference.ts`: `resolveActiveGoalReference(goalRef, activeGoals, { mostRecent })`. Generic, tiered scoring per goal — highest wins: (1) near-exact title match, (2) a *distinctive* token in the reference (length ≥ 6, not a common goal-phrasing word like "book"/"reading"/"goal") fuzzy-matching a title word via plain Levenshtein edit distance (typo tolerance scales with word length — generically covers "Nietsche"/"niezsche"/"nitzche" against a goal titled with "Nietzsche," or any other long/rare word, never a hardcoded name check), (3) generic exact keyword overlap, (4) category match — kept as the *lowest* priority, since treating it as equal-or-higher than a specific match was the original bug. Two or more goals landing within a small margin of the top score return `"ambiguous"` with every near-tied candidate, instead of silently guessing.
- `apps/api/src/agent-runtime/executor.ts`: `resolveGoalReferenceTargets` now calls the new resolver (no `goalRef` still means "report on every active goal," unchanged; a bare pronoun like "it"/"that goal" resolves to the most recently created active goal — `getActiveGoals` already orders newest-first, so this needs no new session state). `goal.status` and `goal.tracking_show` both handle the three real outcomes: `matched` (report on it), `ambiguous` (ask "Do you mean 'Read more' or 'Finish reading Nietzsche book'?" instead of guessing), `no_match` (an honest "I couldn't find an active goal matching X," never a silent fallback to every goal — the previous "empty result only ever means no active goals at all" assumption was the mechanism behind returning the wrong goal).
- `goal.log_evidence`'s `eventType` is now a generically-verified string (checked against the real `EventTypeSchema` registry, exactly how `signalKey` was already checked against `findGoalsForSignalKey`) instead of a hardcoded 5-value enum — any real registered event type an active goal declares can now be logged, not only the original career five. An unrecognized `eventType` is refused with a clear message; a `signalKey` an active goal never declared is refused, unchanged from §21. A new optional `goalRef` arg lets the LLM disambiguate which of several matched goals evidence belongs to when more than one plausibly owns the same signal.
- `goal.create_apply` now includes the newly created goal itself in the turn's `entities` (a new `goalToEntity` helper, matching the existing `actionToEntity`), so it is part of session visible entities immediately, not just its first actions.
- `formatGoalTrackingForChat` now shows a metric's `eventType` (not only `signalKey`) and a check-in's cadence (`GoalCheckInQuestionSchema` gained one additive, JSON-backed optional `cadence` field — the free-form cadence a plan proposed, e.g. "weekly," was previously accepted by `goal.create_propose`/`goal.create_apply` but silently dropped before storage).
- `planner.ts`'s Adaptive Goal Creation guidance now asks for at least one *ongoing* progress signal (e.g. `reading_minutes`/`pages_read`) alongside a completion signal (`book_finished`) for any goal shaped like "finish X" (a book, a course, a project) — generically phrased, not reading-specific — since a plan with only a completion signal gives the user nothing to log or see until the very end. Its Goal Evidence Loop guidance now explicitly steers the LLM toward `goal.log_evidence` (checking `goal.tracking_show` first if the exact key/eventType isn't already known) instead of the untargeted `event.log_custom_progress` whenever a real goal signal could apply, and forbids claiming in `replyDraft` that something was logged "toward"/"on"/"for" a goal unless the executed tool's own result said so.

**Confidence/safety rules honored:** `goal-linking.ts`'s `inferGoalLinkForAction` is untouched and still used for its original job (action→goal domain auto-linking in `action.create`/`gmail.review.to_action`) — this pass added a second, purpose-built resolver rather than changing a matcher other call sites depend on. Every `goalRef`/`eventType`/`signalKey` the LLM supplies is still re-verified against real `context.activeGoals` data before anything happens or any success is claimed, unchanged from §20/§21.

**Tests:** new `tests/agent-runtime-goal-reference.test.ts` (6 tests) reproducing the exact reported scenario — a specific new book goal beating an older generic same-category goal across three different real-world typos of "Nietzsche," an ambiguous reference asking for clarification instead of guessing, a newly created goal visible for an immediate pronoun follow-up, a nonexistent event type refused honestly (proving a failed tool call never lets the planner's pre-execution `replyDraft` leak through as a false success), and an adaptive book-goal plan carrying both a progress and a completion signal end to end. Full suite: **456/456** (450 before this pass + 6 new).

**Validation:** `pnpm typecheck` ✅ · `pnpm build` ✅ · `pnpm test` (456/456) ✅ · `git diff --check` ✅.

**What this closes:** a user with more than one active goal — even in the same category — gets follow-ups resolved against the goal they actually named, typos included; evidence logged for a goal is reliably counted by that same goal's status, or the user is told honestly that it wasn't; and a reply never claims progress was logged unless a real, verified event backs it up.

## 23. Goal Conversation Reliability — session goal focus, guardrail progress-report exemption, optional real-LLM transcript evals (implemented)

A second real Telegram smoke test, once TWO reading goals existed ("Finish reading Meditations by Marcus Aurelius," created first, and "Finish reading Nietzsche book," created second), found: after the bot correctly showed tracking for Nietzsche by name, the very next message — a partial progress report — got intercepted by the goal-aligned guardrail (`goal-guardrails.ts`) and misclassified as a "lapse" against **Meditations**, the wrong goal.

**Root cause of the Meditations/Nietzsche context switch:** §21/§22's `goal.status`/`goal.tracking_show`/`goal.log_evidence` all resolve a `goalRef` against real active goals, but nothing tracked which goal the CONVERSATION was currently about — a bare pronoun/omitted reference fell back to `activeGoals[0]` (the newest-created goal), which is not the same thing as "the goal we were just discussing." Once two goals existed and the user had just been SHOWN a specific, older one by name, the next unnamed message had no way to stay on it.

**Root cause of the guardrail's "avoidance" reply:** `goal-guardrails.ts`'s Tier 2 LLM classification (`classifyGoalConflict`) has no concept of conversational focus either — it's handed the message and ALL active goals, and picks whichever one it judges most related, with no notion of "which goal was this reply actually about." Separately, and more fundamentally: the classifier's own system prompt treats "admitting a missed workout/task" as `soft_warn`/`lapse_admission`, and a partial progress report ("I didn't finish it but I read 30 minutes today") shares the same shortfall-admission shape as a genuine lapse, even though reporting real partial progress toward an ongoing goal is not sabotage of it — it's exactly the evidence `goal.log_evidence` exists to capture.

**Fix — three independent, composable pieces:**
- **Session goal focus** (`apps/api/src/agent-runtime/types.ts`'s new `AgentFocusedEntities`, backed by the `AgentConversationSession.focusedEntities` column — reserved in the schema since its original design, previously always written as `null`): one slot per entity type, updated whenever `goal.status`/`goal.tracking_show`/`goal.log_evidence`/`goal.create_apply` resolve to exactly ONE goal (never for an "all goals" or "ambiguous" outcome), and — unlike `visibleEntities` (a general, whole-list-replaced-per-turn set for numbered-list references) — STICKY: it survives any turn whose own operations don't touch a goal at all, via `runtime.ts`'s new `updateFocusedEntities` (merges per-type, doesn't replace the whole map). `goal-reference.ts`'s `resolveActiveGoalReference` gained a `currentFocus` option, preferred over `mostRecent` for a pronoun/empty reference AND as a tiebreaker when the focused goal is one of several genuinely tied candidates (so "show reading goal" with two plausible goals still asks when nothing is focused yet, but resolves silently to the focused one once something is). The planner's prompt payload now includes `conversation.focusedGoal`, with explicit guidance to pass a pronoun goalRef (e.g. `"it"`) rather than inventing a title when continuing about the focused goal.
- **Guardrail progress-report exemption** (`goal-guardrails.ts`'s new `looksLikeProgressReport`): a deterministic, generic shape check — a quantified activity ("30 minutes," "5 pages," "2 CVs") or an explicit logging phrase ("log it," "logged that") — short-circuits straight to `allow` BEFORE the LLM classification tier is even called, for any of the task's reported examples ("I didn't finish it but I read 30 minutes today," "log it," "I only did 5 minutes," "I missed gym but walked 30 minutes," "I sent 1 CV, not 3"). An explicit user-configured trigger phrase (Tier 1) still always hard-stops regardless of shape; a genuinely non-progress message (no quantity, no logging phrase) still reaches Tier 2 classification exactly as before, so an actual violation is still caught.
- **Generic book/reading progress-signal enforcement, strengthened**: §22 already asked the planner to propose a progress signal alongside completion, but prompt guidance alone didn't reliably produce one (the reported Meditations proposal still came back completion-only). `packages/core/src/goal-evidence.ts`'s new `ensureBookGoalProgressSignal` now DETERMINISTICALLY injects a generic "reading minutes" progress signal into any book/reading-shaped, completion-only proposal, in `goal.create_apply` — the key is derived from the goal's own title (never a shared literal constant across goals, which would make `findGoalsForSignalKey`'s exact-key lookup match the wrong goal). For a goal that predates this fix and genuinely has no progress signal at all, `goal.log_evidence` now tries, in order: (1) remap an LLM-guessed generic key (e.g. "reading_minutes") to the goal's own real progress-shaped metric if one exists (`findCompatibleProgressMetric`, classified off the metric's LABEL only — never its key, which may legitimately contain an unrelated word from the goal's own title); (2) if the goal has a real target goal resolved (by `goalRef` or focus) but only completion signals, ask honestly whether to add a progress signal, rather than silently dropping the evidence or logging it unlinked where `goal.status` could never count it.

**Optional real-LLM transcript eval harness** (`tests/agent-runtime-llm-eval.test.ts` + `tests/helpers/llm-eval-helpers.ts`): the deterministic/mocked-planner suite (unchanged, still the default) can prove the EXECUTOR handles a given tool call correctly, but can never catch the real LLM choosing the wrong tool, the wrong `goalRef`, or misreading a progress report — exactly what both smoke tests actually hit. This new file runs the REAL planner and REAL guardrail classifier (zero mocks) through the same `POST /agent/message` path every other test uses, against a freshly seeded, isolated user, scored on PROPERTIES (`assertNoBannedPhrases`, `assertMentionsGoal`, `assertEvidenceCountedForGoal` — a ground-truth DB check via the same `countEvidenceForMetric` `goal.status` itself uses) rather than exact-text snapshots, since real LLM wording varies turn to turn. **Off by default**: every scenario is registered with node:test's `skip` option unless both `RUN_LLM_EVALS=true` and `OPENAI_API_KEY` are set, so `pnpm test`'s `tests/*.test.ts` glob picks up the file but each test inside it reports "skipped," never "passed" or "failed" — the normal suite stays free and deterministic. Run for real with the new `pnpm test:llm` script (or `RUN_LLM_EVALS=true pnpm test tests/agent-runtime-llm-eval.test.ts` directly). A failing scenario writes a full transcript trace (every turn's message/reply/planned+executed operations/debug info, not just which assertion failed) to `tests/.llm-eval-traces/` (gitignored), via `EvalTrace`. Four scenarios: **A** (reading goal focus — the exact reported shape: create two book goals, show tracking for the older one by name, report partial progress, ask status — asserts no banned wording and real counted evidence on the RIGHT goal, zero on the other), **B** (tea goal — full adaptive create→confirm→log→status flow for a genuinely custom goal), **C** (ambiguous reading reference — two plausible goals, no prior focus, asserts the reply either asks or explicitly names one, never silently merges/guesses), **D** (job goal — existing template goal, "sent 5 CVs today," asserts real counted evidence). This session had no `OPENAI_API_KEY` configured, so these scenarios could not actually be exercised as part of this pass's own validation — confirmed only that they skip cleanly and the harness/scoring code typechecks and builds; running them for real is a follow-up whenever a key is available.

**Confidence/safety rules honored:** the LLM still never decides a real `goalId`/signal/DB mutation directly — `resolveActiveGoalReference`/`findGoalsForSignalKey`/`findGoalsForEventType` still do that deterministically, `currentFocus` only ever changes which goal a PRONOUN or a NEAR-TIE resolves to, never what a specific, clearly-named reference means. The guardrail's explicit-trigger tier (a user-configured hard stop) is untouched and still always fires regardless of message shape; only the LLM-guessed classification tier is exempted for progress-report-shaped messages.

**Tests:** new `tests/agent-runtime-goal-conversation-reliability.test.ts` (8 deterministic tests) — the exact reported transcript shape (focus follows what was shown, not what was newest, partial progress asks honestly against a pre-fix completion-only goal), focus surviving to a later log turn once the focused goal has a real progress signal, the guardrail exemption for a quantified report AND for "log it" (both proven against a deliberately WRONG mocked classification, so a false block would show the exemption didn't work), a genuinely non-progress message still reaching and being blocked by the guardrail, a completion-only book proposal getting a progress signal injected, an ambiguous reference resolving to focus instead of asking, and an existing completion-only goal offering to add a progress signal rather than silently dropping evidence. Plus the new (currently un-run, no API key available) `tests/agent-runtime-llm-eval.test.ts` (4 scenarios, confirmed to skip cleanly). All pre-existing suites (464 tests before this pass) pass unchanged. Full deterministic suite: **464/464** (456 before this pass + 8 new); `pnpm test` overall reports **464 passed, 4 skipped, 0 failed**.

**Validation:** `pnpm typecheck` ✅ · `pnpm build` ✅ · `pnpm test` (464 passed, 4 skipped, 0 failed) ✅ · `git diff --check` ✅. `pnpm test:llm` not run this pass (no `OPENAI_API_KEY` in this environment).

**What this closes:** the conversation now tracks which goal it's actually about, independent of creation order, across turns that don't mention a goal at all; a legitimate partial-progress report is never miscategorized as a lapse or avoidance and never silently blocked from being logged; a book/reading goal always gets a real signal to log ongoing progress against, whether proposed today or predating this fix; and there is now a real (if optional, currently un-exercised) way to catch a future regression in what the LLM itself chooses to do, not only in how the executor handles what it's told.

## 24. LLM eval suite expanded into a product-conversation QA harness (implemented)

§23's 4 scenarios were run for real once `OPENAI_API_KEY` was actually available, and immediately paid for themselves — real runs caught a guardrail false positive (a "want to track a second goal too" statement classified as avoidance of the first), an `eventType`/`signalKey` hedging bug (the planner sometimes sets both; the executor blindly preferred `eventType` even when the target goal only declared `signalKey`), a missing-signal fallback gap (the planner omitting both fields when the target goal has exactly one real signal), and a wrong-tool-choice gap (`event.log_custom_progress` chosen over `goal.log_evidence` despite prompt guidance, producing unlinked evidence with an overclaiming `replyDraft`) — none of which the deterministic suite could see, since it only ever proves the executor handles a GIVEN tool call correctly. Each was closed with a real capability fix (executor.ts's `goal.log_evidence` field-disambiguation and single-metric fallback, `event.log_custom_progress`'s focus-based auto-link, `response-composer.ts`'s `GROUND_TRUTH_ONLY_TOOLS` gaining `event.log_custom_progress`, `goal-guardrails.ts`'s system-prompt clarification for new-goal-intent) — confirmed with the SAME real-LLM scenarios afterward, and the deterministic suite stayed at 464/464 throughout.

**Product decision this section documents:** keep this harness, but explicitly as an optional, manually-run product-conversation QA tool — never default CI, never part of `pnpm test`. `tests/agent-runtime-llm-eval.test.ts` is picked up by `pnpm test`'s `tests/*.test.ts` glob (so it's always present and typechecked), but every scenario inside it registers via `llmEvalOptions(tags)`, which returns node:test's `skip` option unless `RUN_LLM_EVALS=true` AND `OPENAI_API_KEY` are both set — the normal suite reports these as "skipped," never "passed," and the run stays free, fast, and deterministic (**464 passed, 10 skipped, 0 failed** for `pnpm test` after this pass).

**Expanded from 4 scenarios to 10**, chosen to cover Alecto's highest-value user journeys rather than niche edge cases (per the explicit "8-12 scenarios, not dozens" scope):
1. **New user onboarding** (`onboarding`) — an empty user's broad "what should I do?" gets the deterministic goal-anchor nudge (§12) and never fabricates a goal. Included for full-journey coverage even though the nudge itself never calls the LLM (it short-circuits before the planner runs).
2. **Adaptive rare goal — tea** (`adaptive-goal`, `evidence`) — full create→confirm→log→status flow for a genuinely custom, LLM-invented signal.
3. **Book goal — Meditations** (`adaptive-goal`, `book`, `evidence`) — partial reading progress ("read 30min today") is counted and never called avoidance; the direct real-LLM regression test for §23's originally reported bug.
4. **Multiple reading goals** (`goal-reference`, `ambiguity`) — "show reading goal" with two real candidates and no established focus either asks or explicitly names one, never a silent wrong generic pick.
5. **Job-search loop** (`job-search`, `evidence`) — "sent 5 CVs" AND "got 2 recruiter replies" in the same conversation both counted independently (two different `career.*` event types against the same goal).
6. **Gmail recruiter flow** (`gmail`, `job-search`) — a pending, pre-classified recruiter review becomes a real ActionItem, deterministically linked to the job-search goal via the review's own rule (`EmailSignalRule.goalId`).
7. **Gmail admin/bill flow** (`gmail`, `admin`) — the identical mechanism for a fully generic, non-job goal ("Handle Endesa bills"), with an explicit check that the reply never leaks job-search vocabulary ("job"/"recruiter"/"CV"/"application") into an unrelated domain.
8. **Guardrail vs. progress** (`guardrail`, `evidence`) — "I only did 5 minutes today" against a strict daily goal is never called avoidance/sabotage; evidence-logged-or-not is checked only as an informational (non-failing) checkpoint, since that's a narrower signal-matching question addressed by scenario 3, not the guardrail boundary this scenario exists to prove.
9. **Proactive settings** (`proactive-settings`) — "turn on morning briefs" → "yes" → "what proactive messages are on?" actually flips the real `NotificationSettings.morningBriefEnabled` row, checked directly against the DB before and after confirmation, not just reply wording.
10. **Morning brief preview quality** (`morning-brief`, `proactive`) — with job/gym/book goals (each with one real linked action of a different priority) plus a fourth goal with zero actions/activity, the brief leads with the real high-priority action and never mentions the unrelated, actionless goal. Deliberately deterministic under the hood (`decideProactiveOperatorMessage` makes no LLM call — see §13) but included for full-journey coverage; costs no extra OpenAI tokens itself.

**Tooling improvements** (`tests/helpers/llm-eval-helpers.ts`):
- **Tags for subset runs**: every scenario carries `tags` (see the list above); `LLM_EVAL_TAGS=gmail,job-search pnpm test:llm` runs only matching scenarios, everything else reports "filtered out" (a skip, not a failure) — used during this pass's own debugging to isolate scenario 6 without re-running the other 9.
- **Richer failure traces**: `EvalTrace` now also records every checkpoint attempted (via a new `checkpoint(description, passed, detail)` method threaded through all the scoring helpers) — not just the one assertion that finally threw — plus a final DB state snapshot (`captureDbStateSummary`: goals/actions/recent events/Gmail reviews/notification settings) captured at failure time. A failing scenario's dump in `tests/.llm-eval-traces/` (gitignored) now shows the full picture: what was said, what was planned, what actually executed, every property checked and its outcome, and what the DB actually ended up looking like — not just which one line failed.
- **New `assertActionCreated(userId, titleContains, {goalId?})`**: ground-truth DB check for the two Gmail scenarios — a real ActionItem exists (matched by title substring, since the exact title is LLM-authored) and, when `goalId` is given, is actually linked to it.
- **Cost/usage documented directly in the test file's own header comment**: `pnpm test:llm` needs a real `OPENAI_API_KEY` (no mocked path, by design) and costs real API calls — roughly 10 real OpenAI calls total per scenario (2 per turn: guardrail classification + planner), 5-15s each, a small fraction of a cent at `gpt-4o-mini` pricing per full run — intended to be run manually before a major commit, not on every save.

**Deterministic regression tests added this pass:** none — every scenario that failed during this pass's own real runs (`event.log_custom_progress` unlinked evidence, the guardrail false positive, the field-hedging bug, the missing-signal gap) had already been found, fixed, AND given a deterministic regression test in §23; re-running the expanded suite this pass confirmed those fixes hold (9/10 scenarios passed; the one failure was the fallback-planner's own "language model available" text — a transient real API error, reproduced zero times in two follow-up isolated re-runs of the same scenario — not a logic bug, so no new regression test was warranted for it, per the task's own "if it finds a deterministic bug" qualifier).

Scenario 3's "30 minutes" against a goal whose real signal might come back pages-based rather than minutes-based (an LLM-authored unit choice from an earlier turn) remains a known, narrower edge case from §23, unaffected by this pass.

**Tests:** `tests/agent-runtime-llm-eval.test.ts` rewritten from 4 to 10 scenarios (see list above); `tests/helpers/llm-eval-helpers.ts` gained tag-aware `llmEvalOptions`, checkpoint recording, DB-state-snapshot trace dumps, and `assertActionCreated`. Full deterministic suite unaffected: **464/464** pass, this file's 10 scenarios report "skipped" under plain `pnpm test` (474 total, 10 skipped).
